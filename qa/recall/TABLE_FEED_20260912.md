# 表格怎么喂给 LLM：业界调研 + 我们的落地（P1 已完成）— 2026-09-12

## 0. 一句话

**保留 Markdown（不换 HTML），但把"转 Markdown"这件事按业界规范修对**：
矩阵投影 + 多级表头折叠成单行 + 竖线转义。P1 已完成并验证。

---

## 1. 业界调研（只列与我们相关的结论）

| 来源 | 关键结论 | 对我们的适用性 |
|---|---|---|
| **Table Meets LLM**（微软，WSDM'24） | **HTML 最优**（结构理解 96.7% vs Markdown 92.3%）；**Markdown 的 Column Retrieval 断崖式最差（35.3%）**；消融重要性排序：**1-shot 示例 ≫ 问题前置 ≫ 角色提示 ≫ 格式说明**；**自增强"识别关键值与范围"增益最大（+3.26%）** | 结论基于 GPT-3.5/4；**deepseek-chat 未验**，不能照抄格式选择；但"Markdown 列检索差"与我们实测的失败模式**完全一致** |
| **Unstructured（官方）** | 推荐 **HTML**；**不要直接嵌入原始表**（向量模型为自然语言优化）→ **嵌入 LLM 生成的表摘要，完整表挂在 chunk 上**；切分避开表格中间 | 双轨（摘要嵌入 + 原表作答）**直接适用** |
| **Egnyte（企业实测）** | 四格式实测后**选择 Markdown**：**比 HTML 省 40% token**、比 CSV 更能保留层级；连带做法：**表单独存储 + 唯一 ID + 文本打引用标记 + 索引加 Type 字段 + 命中后把整表拉回** | "省 token"这条对我们也成立；重架构不需要（单篇场景） |
| **HtmlRAG** | 粗暴剥离标签会丢结构语义（表格/标题） | 支持"不要压平"，但不支持"必须换 HTML" |
| **中文工程实践** | **Markdown 语法上表达不了合并单元格**；rowspan 会让后续行**少写 `<td>`** → 逐行直转必错位 → 必须**矩阵投影**；多级表头**必须折叠成单行复合列名**；表头行数用 `<thead>`/`<th>` 判定；对 RAG 终局推荐 **linearize 成自然语言** | **我们的 bug 正是这里**，方案可直接照做 |
| **Samuel Ochoa（RAG 文档）** | 按问题形态选粒度（整表/按行/结构化查询）；生产 pipeline **每张表同时产出 Markdown 序列化 + 散文描述，两者都 embed** | 双写做法与我们一致 |

## 2. 我们的决策：**保留 Markdown，不换 HTML**

理由（基于我们自己的约束，不是"不想改"）：
1. 我们的表块**只进检索视图与 L3 上下文，不进 UI 渲染**（cites/高亮走 pymupdf chunk 空间）→ **HTML 的"可直接渲染"优势我们用不上**；
2. **token 代价确定**：Egnyte 实测 HTML 比 Markdown 多 40%；
3. **收益不确定**：HTML 的优势在 GPT-4 上测的，对 deepseek-chat 未知；
4. 换 HTML 要重验所有 markdown 相关链路。

**同时承认 Markdown 有一个固有弱点**（论文实测 Column Retrieval 35%）：不靠换 HTML 解决，靠 **P2 双写**。

## 3. P1 · 已落地（`mineru_bridge.table_to_md`）

改动内容：
1. **矩阵投影** `_grid_project`：按 colspan/rowspan 物理展开成规整二维网格，游标**跳过被上方 rowspan 占走的格子**（用 dict 动态扩张列数，避免"∑colspan 取 max"低估列数）；
2. **多级表头折叠** `_fold_header`：前 h 行沿列拼成 `Story Generation/Pearson` 这样**单行复合列名**（相邻重复去重）；
3. **表头行数判定** `_header_row_count`：`<thead>` → 前导全 `<th>` 行 → **首行含 colspan>1（分组表头）→ 2 行** → 否则 1 行；
4. **竖线转义** `_esc_pipe`：单元格内的 `|` 转 `\|`（MinerU 会产出 `83.3|0.21` 这类单元格，不转义会**串列**）。

### 验证（`_p1_verify.py`，全库 286 张表）

| 指标 | 值 |
|---|---|
| 输出发生变化的表 | **121/286 = 42.3%** |
| 含**多级表头**的表 | **87/286 = 30.4%** |
| 空表头 | **0** |
| **列数不一致（非矩形）** | **0** |
| 总长度 | 208,472 → 236,405（**+13.4%**） |

### 目标表（`75b69eef` / 2002.05058）前后对照

```
旧（错）：  | Task Story Generation | Dialogue |                     ← 2 列
           |---|---|
           | Metric | Spearman | Pearson | Spearman | Pearson |    ← 真列名沦为数据行（5 列 ≠ 2 列）

新（对）：  | Task Story Generation/Metric | Task Story Generation/Spearman | Task Story Generation/Pearson | Dialogue/Spearman | Dialogue/Pearson |
           |---|---|---|---|---|
           | - with skill rating | 0.612(< 0.001) | 0.631(< 0.001) | 0.764(< 0.001) | 0.783(< 0.001) |

```

→ **gold 要的 `0.631`（Story Generation/Pearson）与 `0.302`（ADEM 同行同列）现在一眼可读**。

### 已知代价与遗留

- **长度 +13.4%**：分组表头在跨列上重复。可接受，但若检索层有损，可考虑"紧凑变体"（组名只写一次）；
- **44 张"单列"表**：MinerU 自身把多值挤在一格（如 `SearchSnippetsStackOverflowBiomedical`），**属解析质量问题，非本次改动引入**；
- **caption 粘连未处理**：2002.05058 的 caption 里 Table 1 与 Table 2 两个标题被 MinerU 合成一段，而表体只有一张 → **无法自动判定归属**（需人工看论文），本次**故意不动**，避免引入错误；
- **cvec 缓存已失效**（指纹含文本 md5）→ 下次表通道运行需重编码（33 篇约 40 分钟；176 篇约 2 小时）。

## 4. P3 · 已落地（`answer.py`）

| 改动 | 内容 |
|---|---|
| **问题前置** | 用户问题从消息**末尾**移到**最前**（业界实证：外部信息放在表格之前；放到之后 −6.81%）；`_extract_facts` 的模板同样前置 |
| **条目类型标记** | `_fmt_chunk_entry`：表块 → `[13] 【表格】（p6）：…`，公式 → `【公式】`，正文仍是"正文段落" |
| **一次性表格阅读说明** | 含表时在消息头插入一句「第一行是列名，复合列名用 / 表示层级；先定位列再横向比对」 |
| **facts 按列路径取数** | `SYSTEM_EXTRACT` 新增规则 6：表格按「列路径 → 行标签 → 数值」逐项提取 |
| **表专项抽取（条件触发）** | 见下 |

### 关键实测：**通读式抽取对表的覆盖极不稳定**，所以加了"条件触发的表专项"

同一个 `_extract_facts` 调用（temperature=0）两次：**10 条 facts / 0 条表事实** vs
**54 条 / 31 条表事实** —— 说明"模型不读表"**不是稳定缺陷，而是逐次方差**；
早期基于单条样本下的"抽取器跳过表格"结论**已收回**。

表专项两种策略对照（**36 道含表题**，`_p3_tblab.py`）：

| 策略 | 空手率 | 含数字条数 中位 | 均值 | 最大 |
|---|---|---|---|---|
| **相关性过滤式** | **15/36 = 42%** | 4 | 9.5 | — |
| **宁多勿少全列式** | **0/36 = 0%** | 40 | 62.3 | **301** |

→ 采用 **条件触发 + 全列式 + 代码强制上限 40**：
只在"通读式那一轮没捞到任何表事实"时补跑一次表专项（0% 空手、只在需要时付这次调用）。

### 验证（`_p3_verify.py`，75b69eef）

两次连续运行：通读式 47 / 61 条、均含 **2 条表锚点** → 表专项均未触发；
**两次都含 gold 要的关键数值 4 条**：

```
[13] Story Generation/Pearson → our approach - with skill rating：0.631(< 0.001)
[13] Story Generation/Pearson → ADEM：0.302
```
