## 2. 表池检索 vs 混合池（n=21 可定位目标表的题，表池平均 19 个块）

| 指标 | 混合池 α=0.5（现状） | 混合池 α=0.75 | **表池内 RRF** | 表池内 纯向量 | 表池内 纯BM25 |
|---|---|---|---|---|---|
| 进 top-1 | 1/21 = 5% | 4/21 = 19% | **13/21 = 62%** | 14/21 = 67% | 9/21 = 43% |
| 进 top-3 | 6/21 = 29% | 11/21 = 52% | **17/21 = 81%** | 18/21 = 86% | 18/21 = 86% |
| 进 top-5 | 10/21 = 48% | 12/21 = 57% | **18/21 = 86%** | 19/21 = 90% | 18/21 = 86% |
| 进 top-12 | 14/21 = 67% | 15/21 = 71% | **20/21 = 95%** | 20/21 = 95% | 19/21 = 90% |
| 位次中位 | 7 | 2 | **0** | 0 | 1 |

**机制**：表块在混合池里要和 25~42 个正文块比分数（正文块天然更"像"自然语言查询）；
在表池里它只和 ~19 个同类比，而**向量路本来就能把它排到第 1**（纯向量 top-1 = 67%）。
这解释了为什么"只调权重（α）"收益有限（top-1 只到 19%）——**权重改不了"和谁比"**。

## 3. 为什么"共享池 + 名额保底"不划算

方案：最终候选 = 文本池 top-(12-m) ∪ 表池 top-m（**不需要路由**）。

| 给表池名额 m | 文本侧丢 gold | 表池 top-m 命中目标表 |
|---|---|---|
| 0（现状） | 4/234 = 1.71% | — |
| 1 | 7/234 = 2.99%（净丢 3） | 13/21 = 62% |
| 3 | 15/234 = 6.41%（**净丢 11**） | 17/21 = 81% |
| 5 | 31/234 = 13.25%（净丢 27） | 18/21 = 86% |

→ **腾槽换名额不划算**（净丢 11 个文本题换 +3 个表题）。
→ 但**"并集"（文本 top-12 ∪ 表池 top-3，共 15 块）不丢任何文本题**，代价只是上下文多 3 个块 ⇒ **推荐先做这个**。

## 5. 表块表征现状（核对代码 + 实物）

| 要素 | 现状 | 说明 |
|---|---|---|
| 表头（列名） | ✅ **已有** | MinerU 的 md 保留 `\| Language \| Users \| Docs \| Tokens \| HS Ratio \|` |
| caption | ⚠️ **重复两遍** | `_external_table_chunks` 预置 caption，`element_text` 的 md 里又含一份 → 实测 `xtbl-25` 同一段话出现 2 次，浪费 ~280 字且让 caption 词在 BM25 里权重翻倍 |
| 上下文（正文引用段） | ⭕ **现成可接** | `mineru_bridge.extract_figures_from_mineru` 已算好 `refs`（正文中引用该表编号的段落），只是没喂进表块 |
| 表格解释（LLM 生成） | ❌ 无 | 可选；每篇 ~20 个表，一次性成本极低 |

## 6. 建议的落地顺序

1. **先修表块表征**（零风险，且是任何方案的前置条件）：
   ① caption 去重；② 把 `refs`（正文引用段）拼进表块文本；③ 可选：LLM 生成一句"这表在说什么"。
2. **再做"并集候选"**（文本 top-12 ∪ 表池 top-3）——**不需要路由**，不丢文本题。
3. **路由（硬分池）留到最后**：只有当上下文预算紧张、或要让表池拿更大名额时才需要；
   届时用"问题里的表/数值线索 + 两池分数分布"做软判定即可，不必强分类。

⚠️ **必须记住的教训（同日 α 实验）**：**检索层收益 ≠ 端到端收益**。
α=0.75 在检索层明确改善（表格 MRR +0.12），端到端却分辨不出。
所以上面每一步做完都要在 A 桶 36 题上端到端验证（单臂 ~1 元），不能只看检索指标上线。
