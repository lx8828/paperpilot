# MinerU 表格覆盖率自检（2026-09-12）

> 方法：以 **QASPER 官方 `figures_and_tables` 的 caption 作 ground truth**，
> 与 MinerU 产出的表块标题做匹配（**按内容匹配，不按编号**）。
> 范围：A 桶相关、且有 MinerU 产物的 **33 篇 / 177 张官方表**。
> 复算：`qa/recall/_mineru_coverage.py`（v2），产物 `mineru_coverage_v2_20260912.json`。

## 1. 结果（四分桶）

| 桶 | 数量 | 占比 |
|---|---|---|
| A 内容覆盖 **且编号一致** | 136/177 | **76.8%** |
| B 内容覆盖 **但编号错位** | 12/177 | **6.8%** |
| C **未覆盖（真·漏抽）** | **5/177** | **2.8%** |
| D **无法判定**（该篇 MinerU 表块缺 caption） | 24/177 | **13.6%** |
| **A+B = 内容覆盖** | **148/177** | **83.6%** |

其他：MinerU 表块共 **192** 个，其中 **25 个没有 caption（13%）**；
论文级：有编号错位 **9/33 篇（27%）**、有漏抽 **2/33 篇**、有"无法判定" **11/33 篇**。

## 2. 自我纠错：v1 的 24.9% 漏抽率是**口径缺陷造成的假象**

v1 报"漏抽 44/177 = 24.9%、58% 论文至少漏一张"，经复核是三个缺陷叠加：

1. **罗马数字表号**：官方部分表是 `TABLE I` / `TABLE II`，v1 的编号提取只认阿拉伯数字 → 全部匹配失败；
2. **MinerU 表块可能整个没有 caption**（3 篇的 `n_m=0`）→ 被排除在统计外，既低估覆盖又虚增"漏"；
3. **编号整体错位**（`1909.00088`: 11→13、12→17；`2001.10179`: 2→5、5→6、6→2）→ greedy 匹配把"错位"误算成"漏"。

v2 修掉后：**真·漏抽只有 2.8%**。差一个数量级 —— 这是本项目第 5 次"测量工具骗我"。

## 3. 结论

1. **"MinerU 不行"这个判断基本不成立**：内容覆盖 **83.6%**，真漏抽仅 **2.8%（5 张 / 2 篇）**。
   所以**正确的表绝大多数时候就在语料里**，只是没被正确定位、或没被模型读懂。
2. **真正的风险是"编号错位"**：~~**27% 的论文存在**~~（**数字已作废，见 §5：匹配器夸大，
   可辩护的真错位约 2~3/33 篇**），占官方表 6.8%。
   而我们的**评测口径正是按编号匹配"目标表"**（`_only_table_retr.py` / `_union_prod_eval.py`）→
   在错位的篇上会命中**错的表**（`579941de` 即实例：官方 Table 2 = 性能表，MinerU 的 `xtbl-78` = failure cases）
   → **"并集 +3"的收益要打折**，所有"表格类"检索指标都需重做口径。
   ✅ **2026-09-12 已完成**：新增 `_tgt.py`（**编号 ∪ 内容**联合判定），五个表格脚本全部切换；
   生产链路复算见 `UNION_AND_CONTEXT_20260911.md` §7 —— **并集增益不变（+4 题、零回退）**。
3. **13% 的表块没有 caption**（25/192）→ 只能靠表体文字参与检索（语义弱），也是编号撞车的来源之一。

## 4. 建议（按性价比）

1. **修评测口径**：目标表定位改成「编号 + 表体内容/页码」联合判定（例如：编号一致**且**表体含 gold 数值或表头关键词），否则表格类指标不可信。
2. **给无 caption 的表块补 caption**（13%）：从 MinerU 的 `table_caption` 字段或表体首行推断，提升可检索性。
3. **然后做 oracle 实验**：既然表基本都在（83.6%），就直接问"**把正确的表行喂给模型，它能不能答对**"——
   这一步切开"模型读表能力"与"定位/流程"两个变量，决定后续投在流程还是模型。

## 5. 自我纠错（2026-09-12 追加）：**"27% 论文编号错位"是被我自己的匹配器夸大的**

复核那份 `_mineru_coverage.py` 的 v2 产物，把 12 条"错位"逐条摊开看，性质是这样：

| 性质 | 条数 | 说明 |
|---|---|---|
| 首行确实是 `Table N` 且 N 与官方不同 | 7 | 需再甄别 |
| **该 MinerU 块根本没有 caption** | 3 | 表号=空 → 靠"内容最像"配对，属**任意配对** |
| **该块首行是 `Figure N:`（跨类型）** | 2 | 上游把**图的 caption 拼进了表的 caption** |

而那 7 条里，**caption 文本几乎相同、只是号不同**（强证据）只有 **2 篇**：
`1611.03382`（官方 Table 6 "Visualization of Copy Mechanism" → 表块写 `Table 5`）、
`1911.03243`（官方 Table 2 → 表块写 `Table 4`）。
`1909.00088` 的 4 条落在**附录里 caption 高度雷同**的一组（都是 "Example outputs for an
Amazon/Yelp/news headlines evaluation line..."）→ 匹配器在多个"很像"里任选了一个，**不能当证据**；
`1911.11933` 那条 caption 文本完全不同，**明显假配对**。

→ **可辩护的真错位约 2~3 篇 / 33 篇（6~9%）**，不是 27%。
（"27%"只应读作"**匹配器报出不一致的论文占比**"，不是"编号真的错"。）

### 真正的上游缺陷（已证实，且可在我们这边兜住）

`table_caption` 字段本身被 MinerU 拼了别的东西：

| 论文 | `table_caption` 原文 | 问题 |
|---|---|---|
| `1804.08139` xtbl-3 | `'Figure 6: Attention Distributions... \| Table 4: Average prec...'` | 上方**图的 caption** 被拼进表的 caption |
| `2004.03061` xtbl-2 | `'Figure 1: Derivation of the estimation error. \| Table 3: Accuracies...'` | 同上 |
| `2002.10361` xtbl-33 | `'Age Race Gender \| Table 3: Annotator agreement...'` | **表头行文字**被塞进 caption |

**一张表被判成多个 table 元素**（`2002.10361`: xtbl-58 / xtbl-59 / xtbl-60 表体首行完全相同，
只有 xtbl-60 带 caption）→ 这就是"13% 表块无 caption"的来源。

我们的代码只做 `" ".join(el["table_caption"])`，**没有改号逻辑** → 编号/内容错乱属**上游**；
但**把"编号"当作目标表身份**用的是我们自己的评测口径（`_union_prod_eval.py` / `_only_table_retr.py`
的 `re.match(r"\s*(table|figure)\s*(\d+)")`）→ **口径问题 100% 是我们自己的**，
在错位篇上会量到**错的表**（假阳性/假阴性都有）→ 表格类指标需重做口径后才可信。
