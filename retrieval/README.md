# retrieval/ · 篇级文献检索（找论文）

> 🧭 **本文档是"研究区"口径，与生产区（`src/paperpilot/`）刻意分离**：
> 这里的语料/指标（LitSearch 64,183 篇 · 597 查询）是**评测研究用**；
> 线上"工具① 语料检索"走的是 `src/paperpilot/tools/corpus_search.py` + `retrieval/data/arxiv/`
> （arXiv-only，R@1 0.875 / R@5 0.885）。两者的**流水线逐位一致**，但**语料与分数不可混用**。
> 文档总地图见 `docs/DOC_INDEX.md`。

面向"**给一个研究方向 / 一个问题 → 在几万篇论文里找出目标论文**"的检索层。
它接在 paperpilot 的**上游**：本层负责"找到该读哪几篇"，`src/paperpilot/` 负责
"点进某篇后的结构化精读与引用溯源"。

> 设计依据（为什么单篇上检索无意义、这里才有意义）：判据是 `S / C` 不等式 ——
> 单篇正文中位 6,244 token ≤ 上下文预算，所以直读即可（实测 B0 ≈ B2）；
> 本层语料 6.4 万篇 ≈ 4 亿 token，**任何上下文窗口都放不下**，检索成为物理必需。

## 数据事实（2026-09-18 实测）

**LitSearch**（EMNLP 2024, Princeton NLP）：597 条真实文献检索查询 + 64,183 篇
近期 ML/NLP 论文。查询由 (1) GPT-4 基于带 inline citation 的段落生成、
(2) 论文作者手写，**并由专家逐条人工审核/编辑**。

### query（597 行 / 5 列）

| 列 | 说明 |
|---|---|
| `query` | 查询文本（复杂自然语言，例："Are there any research papers on methods to compress large-scale language models using task-agnostic knowledge distillation techniques?"） |
| `corpusids` | **gold paper IDs（qrels，numpy 数组）** |
| `query_set` | 来源：`inline_nonacl` 42.4% / `manual_acl` 26.0% / `inline_acl` 16.4% / `manual_iclr` 15.2% |
| `specificity` | 0（26%）/ 1（74%）—— 可用于分层 |
| `quality` | 1（49.2%）/ 2（50.8%）—— 可用于分层 |

### qrels 结构（关键）

```
1 个 gold : 563 条 (94.3%)
2 个 gold :  29 条 ( 4.9%)
3 个 gold :   3 条 ( 0.5%)
4 个 gold :   1 条 ( 0.2%)
5 个 gold :   1 条 ( 0.2%)
0 个 gold :   0 条  ← 无不可答题，597 条全部可用
合计 639 个相关判断，均值 1.07
```

**含义**：
- **本质是"单答案检索"**（94.3% 单正例）→ 主指标用 **Recall@k / MRR**
  （nDCG 仍可算，但主要由单正例主导，信息量不如前两者）；
- **候选 64,183 篇** → `Recall@1` 随机基线约 1/64183，**区分度极大**，没有小语料的天花板效应；
- **0 个不可答题**，且（改用 `corpus_s2orc` 补齐 title/abstract 后）
  **639 个 gold 全部有可检索文本** → **597 条查询一条都不用剔除** ✓

### corpus（64,183 篇；**两个 config 都要下**）

| config | 体积 | 字段 | 用途 |
|---|---|---|---|
| **`corpus_s2orc`** | 1.60 GB | `corpusid` · `content.{text, annotations, source}` · `year` · `externalids` | **主数据源** |
| `corpus_clean` | 1.26 GB | `corpusid` · `title` · `abstract` · `citations` · `full_paper` | 兜底 + 引文 + 全文 |

#### ⚠️ 为什么以 `corpus_s2orc` 为主（2026-09-18 实测，重要）

`corpus_clean` 的 title/abstract 是**抽取**产物（README 原文用词 "extracted"），
**约 10% 的记录抽取失败、被存成空字符串** —— 注意是空串**不是 null**，
所以不是读取/解析的问题，是源数据本身如此：

```
corpus_clean 单独 :  title 空 6,760 (10.5%) | abstract 空 7,989 (12.4%) | 双空 6,197 (9.7%)
```

`corpus_s2orc` 的 `content.annotations` 提供 `title` / `abstract` 等实体的
**(start, end) 字符偏移**（JSON 字符串形式），从 `content.text` 切片即得**标注值**
（不是重新抽取）。两源互补后：

```
合并后            :  title 空 1,619 (2.5%)  ← 5,141 篇由偏移补上
                     abstract 空 3,039 (4.7%) ← 4,950 篇补上
                     text 空    914 (1.4%)
```

**这个选择的影响是实质性的**：可用查询 **593 → 597**（不用剔除任何一条）、
可检索文档 **+5,283 篇**、并解锁了 `year` 字段。

**踩坑记录 1**：`title` 标注可能是**多个 span**（如 `[{1,80},{1232,1311}]`，
第二条是页眉/重复标题）。取 min~max 会**把作者块也切进来** →
必须**只取最早那个 span**（见 `build_corpus.py: first_span`）。

**踩坑记录 2（已否决的替代方案）**：用版式启发式从 `full_paper` 猜标题，
人工核对精度仅约 **53%** —— 会把作者名（`Shuaichen Chang`）、机构（`Bosch Center for AI`）、
页眉（`Published as a conference paper at ICLR 2022`）当成标题。**标注 >> 猜测。**

#### 顺带拿到的能力（之前判定为缺失的）

| 字段 | 覆盖 | 解锁 |
|---|---|---|
| **`year`** | **63,725 篇（99.3%）** | **元数据过滤**（"2024 年以后的进展"） |
| `externalids.arxiv` | 15,697 篇（**24.5%**） | arXiv 链接（免费 PDF） |
| `externalids.acl` | 59,385 篇（**92.5%**） | **ACL Anthology 链接 —— NLP 数据集的主源，免费 PDF** |
| `externalids.doi` | 34,891 篇（54.4%） | DOI（多为付费墙，仅兜底） |
| `content.source.pdfurls` | 47,874 篇（**74.6%**） | **PDF 直链**（多为 `export.arxiv.org`；覆盖**超过** `externalids.arxiv`） |
| **三者并集** | **64,181 篇（100.0%）** | **每篇检索结果都能拿到 PDF**；三者全无者仅 **2 篇** |
| `content.annotations.sectionheader` | — | **真章节结构**（优于 ALL CAPS 启发式） |
| `corpus_clean.citations` | 出引文数组，**30.2% 为空** | one-hop 引文扩展（**覆盖约 70%**） |
| `corpus_clean.full_paper` | 中位 48,091 字符，仅 2 篇为空 | 全文 → **接精读链路无需下载 PDF** |

### 规模（这是"检索必需"的最硬证据）

```
单篇全文中位   48,091 字符 ≈ 12,000 token      ← 比 QASPER（6,244）大一倍
全语料规模     64,183 × 12,000 ≈ 7.7 亿 token
上下文预算     64K ~ 1M token
S / C ≈        770 ~ 12,000 倍                 ← 放不下，且差三个数量级
```

### 编码成本（论文级 vs 切块级）

按 `build_corpus.py` 实测：**63,269 篇有文本**，`text`（title+abstract）中位 936 字符、
合计 **约 20 M token**。

| | 论文级（title+abstract ≈ 290 token） | 切块级（全文 ≈ 12,000 token） |
|---|---|---|
| 编码量 | 63,269 × 1 向量 | 63,269 × ~20 块 ≈ **130 万块** |
| GPU 4050 时间 | **约 10~30 分钟** | 约 1.5~3 小时 |
| 向量存储 | **259 MB**（63,269 × 1024 × 4B） | **5 GB** |

→ **只做论文级索引**（LitSearch 的 qrels 也是论文级的）；段级证据按需在
top-k 篇上现算（几十篇 × 20 块），成本可忽略。**不需要给 6.4 万篇全部切块。**

## 评测设计（待落地）

两层，各用合适的集合：

| 层 | 用什么 | 指标 | 状态 |
|---|---|---|---|
| **篇级召回** | LitSearch（64,183 篇） | Recall@1/5/10、MRR@k | 本次要建 |
| **段级证据** | QASPER（426 篇，段落级 gold evidence） | Recall@k、nDCG@10 | 已有（`cli/run_retrieval_eval.py`） |

消融对照（每项都要给"有效/无效 + 原因"，而不是只报数字）：

```
A. BM25
B. dense（bge-m3 / 领域模型）
C. hybrid（RRF，含 α 扫描）
D. C + cross-encoder rerank
E. D + 元数据过滤 / one-hop 引文扩展
```

**分层报告**（这是"有观点"的关键，而不是只报一个总分）：
- 按查询是否含**精确 token**（专有名词 / 缩写 / 数字）分组 → 解释混合检索的收益边界；
- 按 `specificity` / `query_set` 分组 → 解释不同查询类型的难度。

## 结果：完整消融（2026-09-18，597 题，63,269 篇）

| 配置 | R@1 | R@5 | R@10 | R@100 | MRR@10 |
|---|---|---|---|---|---|
| BM25（jieba 式小写分词 + Okapi，k1=1.5/b=0.75） | 0.2588 | 0.4367 | 0.5238 | 0.7118 | 0.3457 |
| dense（`BAAI/bge-m3`，归一化余弦） | 0.2965 | 0.4939 | 0.5732 | 0.7934 | 0.3887 |
| **hybrid RRF α=0.5** | 0.3498 | 0.5436 | 0.6059 | **0.8160** | 0.4459 |
| hybrid RRF α=0.7 | 0.3632 | 0.5520 | 0.6260 | 0.8059 | 0.4566 |
| **+ rerank `BAAI/bge-reranker-v2-m3`（重排 α=0.5 的 top-100）** | **0.4154** | **0.6118** | **0.6712** | 0.8160 | **0.5072** |

**全链 R@1：0.2588 → 0.4154（+15.7pt，相对 +60%）**，每一步统计显著。

### 显著性（`results/LITSEARCH_SIGNIFICANCE.md`、`LITSEARCH_RERANK.md`）

方法：**McNemar 精确检验**（二元 hit@k）+ **配对 bootstrap**（连续 Recall/MRR，10k 次重采样）。
不能用双样本检验 —— 所有系统跑同一批题，"谁在哪题赢"是强相关的配对信息。

| 对比 | 指标 | 增益 | 显著性 |
|---|---|---|---|
| dense vs BM25 | hit@1 | 净 +23 | **p=0.0505 不显著** |
| dense vs BM25 | recall@10 / mrr@10 | +4.9pt / +4.3pt | 显著（p=0.018 / 0.007） |
| hybrid α=0.7 vs dense | recall@1 | **+6.67pt** | **p≈0（CI [+3.74, +9.63]）** |
| hybrid α=0.5 vs BM25 | recall@1 | +9.10pt | **p≈0** |
| + rerank vs hybrid | recall@1 | +6.56pt | **p=0.0002** |
| + rerank vs hybrid | hit@10 | 净 +39 | **p=9.8e-06** |
| hybrid α=0.7 vs α=0.5 | recall@1 | +1.3pt | 不显著（CI 跨 0） |

### ⚠️ 反直觉结论：**dense 单独的优势很弱**

`dense vs BM25` 在 **hit@1 上 p=0.0505（不显著）**、recall@1 的 CI 下界贴着 0
（[+0.17, +7.45]），只在 R@10/MRR 上稳定显著。
→ 在这个语料上**"换更强的 embedding"的收益有限，主要收益来自"把 BM25 融进来"**。

**caveat**：LitSearch 论文称 "dense 显著优于关键词检索"，我们没复现出那么强 ——
很可能因为论文用的 GTR / E5 / Instructor / GritLM 强于 `bge-m3`。
**故"dense vs BM25 谁强"依赖模型选择，不可外推。**

### 判据：混合检索的价值 ∝ 两路的分歧程度

| 查询类型 | dense vs BM25 | hybrid α=0.7 vs dense |
|---|---|---|
| **含精确 token**（大写缩写/数字，n=101） | Δ=**−1.5pt，不显著**（p=0.79） | **+13.4pt，显著**（p≈0） |
| **纯自然语言**（n=496） | +4.8pt，**显著**（p=0.019） | +5.3pt，**显著**（p=0.0008） |

> 两路势均力敌时（含精确 token）融合收益最大（+13.4pt）；
> 一路明显碾压时（纯自然语言，dense 强）收益较小（+5.3pt）但仍显著。
> **这个判据比"混合检索涨了 6.7 个点"有操作价值。**

另按查询来源：**作者手写**（manual_acl/manual_iclr）上 **BM25 反而强于 dense**；
**GPT-4 生成**（inline_*）上 dense 强于 BM25；而 hybrid 在四类上全部最好。

### α 的选择：由下游决定（差异本身不显著）

`α=0.7 vs α=0.5` 在 recall@1 上 **CI 跨 0**（p=0.126）。选哪个看下游：
- **要上 rerank** → 选 **α=0.5**（R@100 最高 0.816，精排才有东西可排）
- **不上 rerank** → 选 α=0.7（R@1 最高）

**精排上限 = 基线 R@100 = 0.816**（重排无法召回新文档）—— 所以先保召回、再修排序。

### 样本量的教训（两次撞到）

| | 20~40 题冒烟 | 597 题全量 |
|---|---|---|
| hybrid vs dense（R@10） | 冒烟显示 hybrid **更差** | 全量显示 hybrid **显著更好** |
| rerank 增益（R@1） | +22.5pt | **+6.6pt** |

小样本会给出**方向相反或夸大数倍**的结论。**结论必须跑满 597 题**（`--limit` 只能用于验证链路）。

## L1 意图识别与查询分流（2026-09-18）

### ① Broad / Specific 分类评测（`classify_specificity.py`）

LitSearch 自带真值：`specificity`（论文 Table 1：**Broad = 语料中可满足 >5 且 ≤20 篇**；
**Specific = ≤5 篇**；作者团队逐条人工标注）。分布 Broad 155 / Specific 442，与论文 Table 2 一致。

> ⚠️ **这个任务不平凡**：判定标准是"**语料里有多少篇能满足**"（语料依赖 + 知识密集），
> **不是**"查询文字看着抽象还是具体"。实测两类表面统计差异极小
> （字符数中位 134 vs 137、词数中位都是 19）。

| 分类器 | accuracy | Broad P | **Broad R** | Broad F1 | Specific R |
|---|---|---|---|---|---|
| **A. 多数类**（全猜 Specific） | **0.7404** | 0.000 | **0.000** | 0.000 | 1.000 |
| B. 表面特征 + LR（5折CV） | 0.5075 | 0.299 | 0.665 | 0.412 | 0.453 |
| D. 检索分布 + LR（5折CV） | 0.5997 | 0.359 | 0.690 | 0.472 | 0.568 |
| **C. LLM 零样本** | 0.7102 | 0.457 | **0.619** | 0.526 | 0.742 |

**成本**：557 次调用 / 129.7K+26.6K token / 58 秒 ≈ **$0.02**。

三条结论：

1. **accuracy 在这里会骗人**：全猜 Specific 的 accuracy **更高**（74.0% > 71.0%），
   但 **Broad recall = 0** → 路由永不触发扩展。**Broad recall 才是这个任务的真指标。**
2. **LLM 是唯一有实质区分度的**（Broad recall 0.619），但 71% **不超多数类基线** →
   不足以支撑硬路由（与 `RAG_COMPONENT_NOTES §2` 那条教训同因）。
3. **"检索分布"信号（D）不如预期**（0.5997）。原因：`specificity` 是**全语料的全局属性**，
   而所用特征几乎全在 top-100 内 → 看不到长尾。**这是可反驳的负结果**（换 top-1000 或拟合
   整条分布形状可能不同）。

### ② 负结果：`specificity` **不构成分流的依据**（`stratify_queries.py`）

路由的收益 = `P(分类对) × (扩展策略收益 − 不扩展收益)`。所以先做**前置验证**：
两组的最优策略是否真的不同？

| 组 | n | best(R@1) | best(MRR) | hybrid 增益（hyb0.7 − dense） |
|---|---|---|---|---|
| 真值·Broad | 155 | **hyb0.7** | **hyb0.7** | +2.80pt（13.8%） |
| 真值·Specific | 442 | **hyb0.7** | **hyb0.7** | +8.03pt（24.4%） |
| 预测·Broad | 210 | hyb0.7 | hyb0.7 | +2.86pt（12.1%） |
| 预测·Specific | 387 | hyb0.7 | hyb0.7 | +8.74pt（26.5%） |

**两组的最优配置完全相同、六路的相对排序也完全一致** → 分流后两边执行的是**同一个**策略
→ **分流没有收益，只增加分类错误的风险。故 L1（按 specificity 路由）不做。**

三个副结论：

- Broad 组整体更难（R@1 0.23 vs 0.41），但 **"更难" ≠ "需要不同策略"**；
- **混合增益在 Specific 组反而更大**（24.4% vs 13.8%），**与"宽泛问题更适合融合"的直觉相反**
  （可能因为 Broad 目标论文多、召回本就容易，Specific 只有 1~5 篇、更依赖 BM25 的精确匹配）；
- LLM 预测分组给出与真值组**同向**的模式（+12.1% vs +26.5%）→ **分类器的信号是真的，
  只是不落在"策略分歧"上**，所以无法用于路由。

**推论（决定后续顺序）**：真正可能构成分流依据的，是**尚未实现的扩展型策略**
（L3 改写 / L5 分解）。"宽泛问题该扩展"必须等扩展策略**本身有效**后才能测
—— **所以顺序不可颠倒：先做 L5 / L3+`quota_union`，最后才考虑 L1。**

### ③ 路由的理论上界：`oracle_routing.py`（通用工具，配置变了就重跑）

路由的收益**不可能超过 per-query oracle**（假设完美路由器，每题都选到当下最优配置）。
若连 oracle 的领先都很小，任何路由器都不值得做。

| 指标 | 全局最优固定（hyb0.7） | per-query oracle | headroom |
|---|---|---|---|
| recall@1 | 0.3632 | 0.4578 | **+0.0946（+26.1%）** |
| recall@10 | 0.6260 | 0.6995 | +0.0735 |
| mrr@10 | 0.4566 | 0.5496 | +0.0930 |

**但 headroom 拆开看，一半是噪声（这是关键闸门）**：

| 配置子集 | oracle | 相对 hyb0.7 |
|---|---|---|
| 全部 6 个 | 0.4578 | +0.0946 |
| **hyb 家族 4 个（同一管道不同 α）** | 0.4109 | **+0.0477 ← 噪声** |
| 仅 `{bm25, dense}`（质性不同） | 0.3819 | +0.0187 |

- hyb 家族 4 个配置在 **85.4%** 的查询上结论完全一致；**存在唯一胜者的查询仅 22 条**，
  且散布在各 α 间（hyb0.9 赢 12 / hyb0.3 赢 7 / hyb0.7 赢 3）→ **无模式 = 采样噪声，不可学**；
- 即 **+4.77pt 的天花板哪怕分类器 100% 准也拿不到**；
- 另一半 +4.69pt 来自 `bm25 vs dense` 的**质性差异**，理论上可学，但**不由 `specificity` 决定**。

**按标签分组的 oracle（= 完美分类器的上限）**：

| 标签 | recall@1 | recall@10 | mrr@10 |
|---|---|---|---|
| 真值 `specificity` | **+0.0000** | +0.0000 | +0.0000 |
| LLM 预测 | +0.0000 | +0.0025 | +0.0000 |

**5 折 CV 的诚实路由收益（仍假设标签免费且完全准确）全部为负**：
真值标签 −0.0109（R@1）/ LLM 预测 −0.0042 → **组内选最优的噪声吃掉了全部收益**。

**一致性**：hyb0.7 在 **90.5%**（R@1）/ 92.1%（R@10）/ 74.9%（MRR）的查询上
**已是最优或并列最优** → 路由的着力面只有 9.5%。

> **结论**：路由要成立需要**两个**条件 ——
> ① 候选策略之间存在**质的差异**（现在 6 个里 4 个是同一管道的 α 取值）；
> ② 存在**可观测标签**能预测"哪类查询该用哪个"（`specificity` 已证否）。
> **现在两个都不满足，所以不分流。** 等 L3/L5/L4 落地（候选之间才有质的差异）后，
> **直接重跑本脚本**即可回答"路由是否到了该做的时候"。

## 池子深度扫描（阶段 A：`eval_retrieval.py --topk 1000 --curve ...`）

### ⚠️ 先修一个真 bug：**RRF 组件列表被截断到与输出同长**

现象：`--topk 100` 与 `--topk 1000` 两次运行的 **hybrid 结果对不上**（前 100 列重合度仅 **0.87**），
而 `bm25`/`dense`（不经过融合）完全一致（1.000）。

根因：`rrf_fuse([rd, rb], ...)` 的 `rd`/`rb` 只有 100 长，输出也要 100。
**RRF 靠 rank 计分** —— 组件列表被截断后，排名 101~1000 的文档在融合里得到 **0 分**，
于是输给"只是同时出现在两个 top-100 里"的文档。

| 影响 | 说明 |
|---|---|
| 旧基线 hybrid 数字 | **系统性偏低**（`hyb0.5` R@100 0.8160 → **0.8350**） |
| `rerank_scores.npy`（+6.6pt 那次） | **在一个次优池子上测的** → 真实上界更高 |
| `per_query.parquet` | 已被修正后的运行覆盖 |

修复：新增 `--fuse-in`（**组件列表深度，默认 1000**），并强制 `fuse_in ≥ topk`。
> **规则：RRF 的组件列表必须显著长于输出深度。**

### Recall@k 曲线（`--topk 1000 --curve 1,5,...,1000`，6 系统 × 9 档）

**R@k 就是"池子开 k"时的召回率 = 精排 R@1 的理论上界。**

| 配置 | R@1 | R@5 | R@10 | R@20 | R@50 | R@100 | R@200 | R@500 | R@1000 |
|---|---|---|---|---|---|---|---|---|---|
| bm25 | 0.2588 | 0.4367 | 0.5238 | 0.5920 | 0.6624 | 0.7118 | 0.7648 | 0.8449 | 0.8923 |
| dense | 0.2965 | 0.4939 | 0.5732 | 0.6550 | 0.7289 | 0.7934 | 0.8430 | 0.8887 | 0.9190 |
| hyb0.3 | 0.3255 | 0.5319 | 0.5987 | 0.6364 | 0.7073 | 0.8050 | 0.8609 | 0.9110 | 0.9354 |
| **hyb0.5** | 0.3548 | 0.5475 | 0.6174 | 0.6978 | 0.7838 | **0.8350** | 0.8673 | 0.9093 | **0.9379** |
| hyb0.7 | 0.3649 | 0.5542 | 0.6293 | 0.6959 | 0.7841 | 0.8299 | 0.8665 | 0.9088 | 0.9341 |
| hyb0.9 | 0.3431 | 0.5341 | 0.6017 | 0.6687 | 0.7414 | 0.8034 | 0.8481 | 0.9030 | 0.9257 |

**三个读数**：

1. **"召回已经差不多了"不成立**：`hyb0.5` R@100 = 83.5% → R@1000 = 93.8%，
   **top-100 之外还压着 10.3pt 的 gold** → **扩池子是"白捡的召回"**（不换模型、不动查询侧）；
2. **边际增益不单调递减**：`→200 +3.2pt` 却 `→500 +4.2pt`、`→1000 +2.9pt`
   → 长尾里是**成批**的 gold，到 1000 都没停；
3. **`K_cand` 与 `α` 耦合（必须联合扫）**：
   ```
   k=1,5,10,50 → hyb0.7      k=20,100,200,1000 → hyb0.5      k=500 → hyb0.3
   ```

**相对 k=1000 的达成率（%）** —— 决定池子开多大：

| 配置 | k=100 | k=200 | k=500 |
|---|---|---|---|
| hyb0.5 | 89.0 | 92.5 | **96.9** |
| dense | 86.3 | 91.7 | 96.7 |
| bm25 | 79.8 | 85.7 | 94.7 |

→ **k=100 丢掉 11% 的可召回 gold；k=500 只丢 3.1%。**

**排序空间修正**：`R@100 = 83.5` vs `R@1 = 36.5` → **47pt 的排序空间**（此前估 40pt）。

## 阶段 B：精排深度扫描（**负结果：扩池子无效**）

```
rerank_eval.py --topk-file topk1000.npz --base hyb0.5 --topk 1000 \
               --max-length 512 --batch 64 --depth-sweep 100,200,300,500,1000
```
597 题 × 1000 = **597,000 对**；4050 上 **87 对/s → 114.6 分钟**（探针预估 89 对/s，准）。

| K_cand | 池子上界 R@K | R@1 | R@5 | R@10 | R@20 | MRR@10 | 吃掉排序空间% | 成本(万对) |
|---|---|---|---|---|---|---|---|---|
| **100** | 0.8350 | **0.4154** | **0.6168** | **0.6735** | **0.7430** | **0.5073** | 12.62 | 6.0 |
| 200 | 0.8673 | 0.4137 | 0.6135 | 0.6729 | 0.7321 | 0.5060 | 11.49 | 11.9 |
| 300 | 0.8899 | 0.4137 | 0.6084 | 0.6712 | 0.7338 | 0.5051 | 11.01 | 17.9 |
| 500 | 0.9093 | 0.4137 | 0.5992 | 0.6662 | 0.7321 | 0.5033 | 10.62 | 29.9 |
| 1000 | 0.9379 | 0.4137 | 0.6009 | 0.6679 | 0.7371 | 0.5032 | 10.10 | 59.7 |

**结论：扩池子对精排零收益，且轻微有害。**

1. **池子上界 83.5% → 93.8%（+10.3pt），但精排 `R@1` 完全不动**（0.4154 → 0.4137）；
2. **`R@5` 反而 −1.59pt**（0.6168 → 0.6009）→ **长尾候选在"挤掉"好的结果**；
3. **`K_cand ≥ 200` 时 `R@1` 是完全相同的 0.4137** → 新增候选对 top-1 **毫无贡献**；
4. 成本却涨 **10 倍**（6 万 → 59.7 万对）。

**机制**：cross-encoder 判别力有限 —— 候选越多，"看起来相关但不对"的干扰项越多，
它们与真金的打分差很小，于是把真金挤下去。

**副作用**：`K_cand = 100` 时 `R@1 = 0.4154`（与旧池一致），但 `R@5 = 0.6168`
（旧池 0.6118）→ 修正 RRF 后同一配置已略好。

**修正"排序是最大战场"这个判断**：

| 原判断 | 修正 |
|---|---|
| 排序有 47pt 空间（`R@100 83.5` vs `R@1 36.5`） | **几何上对，但现有精排器只能吃 12%，且加深池子无法提高** |
| 先扩池子、再换精排 | **扩池子是负收益，跳过** —— `K_cand = 100` 即最优 |

→ **要吃到那 47pt 只能换精排策略**（轴②更强模型 / 轴③输入粒度 / 轴④分数融合），
**不能靠加深池子**。

## 阶段 ①：纯 listwise 精排（**大幅正收益**）

`llm_rerank.py`：每条查询 **1 次调用**，K_LLM=20，呈现顺序**已打乱**（缓解位置偏差）。

**臂 B 是干净对照** —— 给 LLM 的 20 篇与 cross-encoder 的 top-20 **完全相同**，
唯一变量是"谁排序" → 直接隔离 **listwise vs pointwise**。

| 臂 | 方法 | R@1 | R@5 | R@10 | R@20 |
|---|---|---|---|---|---|
| B | cross-encoder（pointwise，同候选集） | 0.4154 | 0.6168 | 0.6735 | 0.7430 |
| B | **LLM listwise** | **0.6092** | **0.7195** | **0.7271** | 0.7430 |
| A | 池子前 20（基线） | 0.3548 | 0.5475 | 0.6174 | 0.6978 |
| A | **LLM listwise** | **0.5598** | **0.6802** | **0.6928** | 0.6978 |

- **臂 B：R@1 0.4154 → 0.6092（+19.4pt）**；McNemar 仅 LLM 命中 133 / 仅基线 14，
  净 +119，**p = 1.7e-25**（极度显著）；
- 输出格式干净率 **100%**（严格"1..K 排列"校验，缺项补位、重复丢弃），失败 0 次；
- 成本 **1182 次调用 / 4.93M prompt + 74K completion token ≈ $0.7~1.3**。

### 最有说服力的数字：**上界利用度**

| 精排范式 | 吃掉的排序空间 |
|---|---|
| pointwise（cross-encoder） | **16.7%** |
| **listwise（LLM）** | **59.2%** |

→ **listwise 的利用效率是 pointwise 的 3.5 倍**（同样的候选集、同样的上界）。

> 扩池子对 pointwise 精排 **0 收益** —— **不是"排序没空间了"，而是"pointwise 吃不到"**。
> 换成 listwise，**同样那 20 篇候选**，R@1 就高了 **19.4pt**。
> **瓶颈在范式，不在池子深度。**

## 阶段 ①-B：信息量阶梯（**全文不可替代，压缩有损**）

```
llm_rerank.py --arms B --doc-views title,short,kw,full
```
臂 B = 与 cross-encoder **同候选集**（只改排序）；各 view 的**呈现顺序完全相同**
（同 seed 重置 rng）→ 「信息量」是唯一变量。K_LLM=20，597 条。

| view | 喂什么 | R@1 | R@5 | R@10 | 吃掉排序空间% | tok/查询 |
|---|---|---|---|---|---|---|
| `title` | 仅标题 | 0.5243 | 0.6919 | 0.7262 | **33.3%** | 650 |
| `short` | 标题 + 摘要前 100 字符 | 0.5255 | 0.6919 | 0.7195 | **33.6%** | 1,129 |
| `kw` | 标题 + 高 IDF 关键词（本地免费） | 0.5137 | 0.6953 | 0.7212 | **30.0%** | 1,306 |
| **`full`** | 标题 + 摘要前 1000 字符 | **0.6092** | **0.7195** | **0.7271** | **59.2%** | ~4,000 |

（基线 cross-encoder：R@1 0.4154；上界 0.7430。全部 view 格式干净率 100%、均显著）

**四条结论**：

1. **`title → full`：R@1 +8.5pt**，上界利用度 **33.3% → 59.2%（接近翻倍）**
   → **摘要的论述内容是判相关性的主要依据**；
2. **`short` ≈ `title`**（+0.12pt）→ 摘要前 100 字符基本只是标题的重复；
3. **`kw` 比只给标题还差**（−1.06pt）→ 关键词列表丢失了
   **"这篇论文在解决什么问题"这个最关键信号**；
4. `kw` 的 R@5/R@10 反而略高于 title（0.6953/0.7212）→ **能挤进前几名，但选不准第一名**。

### 对 CoRank 的含义（关键澄清）

| 可能的归因 | 实测 |
|---|---|
| "压缩省 token" | ❌ 压缩本身**有害**（−8.5pt） |
| "**用紧凑表示做粗排以扩大范围**" | ✅ 这才是它的机制 |

CoRank **不是"用紧凑表示替代全文"** —— 它是三阶段：
`① 离线抽特征 → ② 紧凑表示粗排（覆盖 200 篇）→ ③ 对 top-20 用全文细排`。
**最终排序仍然靠全文** → 其价值是**扩大范围**，与本实验结论**一致而非矛盾**。

> ⚠️ 诚实说明：本实验的 `kw` 是**免费近似**（IDF 选词），不是 CoRank 的 LLM 抽取特征，
> 因此对该方法的对比不完全公平。但即便完美的关键词表也难以传达
> "问题—方法—结论"的命题结构，而这正是 `full` 相对 `title` 多出 8.5pt 的来源。

### 对阶段 A（K 扫描）的影响

**A 应当继续喂全文**：全文 184 token/篇 × 100 篇 = **18.8K token，放得下 64K**
→ K 可直接扫到 100，**不需要为省 token 而压缩表示**（细排必须全文）。

**仍有希望**，可作为后续选项。

## 阶段 ②-B：廉价表示能否用于粗筛？（**免费预测试 → 否**）

**动机**：K 扫描证明"多花钱只能买 R@20、买不到 R@1"，于是核心问题变成
**「怎么把 top-100 筛成 20」**（筛选质量 = 上界瓶颈）。而"LLM 看 100 篇全文再筛"
（18.8K + 4.1K = 22.9K token）**比 K=100 单次还贵** → 只有**粗筛能用廉价表示**时才划算。

**做法**（`screen_cheap_probe.py`，纯 GPU 免费）：用 cross-encoder 作代理，
把候选表示换成 `title` / `short`(标题+前100字符)，重跑 top-100。

| 表示 | gold@top1 | gold@top5 | gold@top10 | **gold@top20** | gold@top50 | gold@top100 |
|---|---|---|---|---|---|---|
| **full（现用）** | 0.4154 | 0.6168 | 0.6735 | **0.7430** | 0.8132 | 0.8350 |
| `title` | 0.2669 | 0.4613 | 0.5342 | **0.6373** | 0.7470 | 0.8350 |
| `short` | 0.2638 | 0.4445 | 0.5329 | **0.6130** | 0.7487 | 0.8350 |

**差值**：`title` top-20 **−10.57pt**；`short` top-20 **−13.00pt**。

### 结论：廉价表示不能用于粗筛

→ 「LLM 看 100 篇廉价表示筛 20」路线**放弃**（省下 ~$2.5）。
初筛就掉 10.6pt，远超"便宜 3 倍"能弥补的。

### 为什么"筛选是松任务"这个推理错了（重要）

候选池里的 100 篇**全都是同一主题** —— 因为它们本来就是第一阶段**按语义**召回的（`hyb0.5`）。
**所以在主题层面它们全都"相关"，区分它们必须靠"论证细节"，而标题里没有这个信息。**

这正是**同质干扰项**的典型表现，与"阶段① 混合检索增益小"同源。

**直接证据**：`gold@top100` 三种表示**完全相同（83.5%）** → 候选集合一样，
**差异只体现在排序上** → 「信息量」影响的是**区分能力**，不是**召回范围**。

**副产品**：`short` **比 `title` 还差** → "标题 + 前 100 字符"是**坏表示**
（摘要开头多为 "Recently, … has attracted attention…" 这类无信息量套话，噪声多于信号）。
→ 以后复用摘要做短表示时，**不要取开头**。

### 成本结论（完整版）

| 方案 | tok/查询 | $/千次 | R@1 | R@20 |
|---|---|---|---|---|
| **K=20 + cross-encoder 过滤（现用）** | 4,082 | **$0.6** | 0.6092 | 0.7430 |
| K=50 | 10,049 | $1.4 | 0.6092 | 0.7956 |
| K=100 | 19,304 | $2.7 | 0.6092 | 0.8132 |
| ~~两轮（LLM 筛 100 全文 → 精排 20）~~ | 22,880 | $3.2 | 未知 | ~0.813 |

> **K=20 是"R@1 优先 + 成本敏感"下的正确选择。理由不是"便宜"，而是
> 「K=100 多花 4.5 倍的钱，**买不到任何 R@1 提升**，只能买 R@20」** ——
> 这是成本-收益判断，不是省钱。面试时应这样表述。

### 时间成本实测（`latency_probe.py` → `LITSEARCH_LATENCY.md`）

钱算完后只剩**延迟**一个决策变量，于是实测（30 题配对 × 每档 3 次取中位，
**流式**计时拆 TTFT / 总耗时，两档顺序随机化排除负载漂移，预热 1 次不计）：

| 指标 | K=20 | K=50 | Δ | 95%CI | 显著 |
|---|---|---|---|---|---|
| TTFT(prefill) | 596ms | 620ms | **+24ms** | [−54, +68] | 否 |
| **总耗时** | **840ms** | **1135ms** | **+295ms（1.35×）** | [+208, +350] | **是** |
| 格式干净率 | 100% | 100% | — | — | — |
| completion token | 63 | 153 | ×2.43 | — | — |

**最有价值的发现是"瓶颈不在我们以为的地方"**：

```
prompt token   ×2.38  →  TTFT 只 +24ms（不显著）    ← DeepSeek prefill 太快了
completion tok ×2.43  →  总耗时 +295ms（占全部增量） ← 全部来自"多输出 30 个数字"
```

> **所以 K=50 的代价是"多等 0.3 秒"，不是"多花 2.46 倍的钱"** ——
> 钱的绝对值（+$0.84/千次）在任何商业场景下都不构成约束。

**由此暴露一个优化方向 → 已验证，见下节。**

### 「只输出前 10 名」：**把池子深度与输出长度解耦**（`partial_out_probe.py`）

既然代价全在"输出 50 个数字"，而交付只要 top-5，就让 LLM **只给前 10 名**。
三臂共用同一池子，只改**候选数**与**输出长度**（温度 0，顺序随机化）：

| 臂 | R@1 | R@5 | R@10 | TTFT | **总耗时** | prompt_tok | comp_tok | 格式干净率 |
|---|---|---|---|---|---|---|---|---|
| `k20` | 0.6181 | 0.7179 | 0.7329 | 568ms | 825ms | 4,237 | 63 | 100% |
| `k50` | 0.6298 | 0.7511 | 0.7772 | 632ms | **1147ms** | 10,129 | 153 | 99.8% |
| **`k50p10`** | 0.6214 | **0.7528** | **0.7830** | 645ms | **813ms** | 10,172 | **33** | **100%** |

**配对显著性**（全 597 题）：

| 对比 | 指标 | Δ | 95%CI | 显著 | p |
|---|---|---|---|---|---|
| `k50p10 − k20` | **R@5** | **+3.50pt** | [+1.65, +5.40] | **是** | **5.1e-04** |
| `k50p10 − k20` | R@10 | +5.01pt | [+3.17, +6.95] | 是 | 6.0e-07 |
| `k50p10 − k50` | **R@5** | **+0.17pt** | [−0.92, +1.26] | **否** | 1.0 |
| `k50p10 − k50` | R@10 | +0.59pt | [−0.17, +1.42] | 否 | 0.375 |

```
相对 k20：R@5 +3.50pt（显著）     总耗时  −11.7ms（825 → 813ms，略快）
相对 k50：R@5 +0.17pt（不显著）   总耗时 −333.3ms（1147 → 813ms）
```

**结论：兼得，验证通过。**

1. **保住 K=50 的全部召回**：R@5 差 **+0.17pt**，CI 跨 0，p=1.0；R@10 也略高；
2. **拿回 K=20 的延迟**：813ms vs 825ms，**甚至略快 11.7ms**；
3. **格式干净率 100%**（输出 10 个数字零失误）；反而 `k50`（输出 50 个数字）有 1 次不干净。

机制：`prompt` 仍 ~10K（TTFT +77ms）被 `decode` 缩短（−346ms）抵消 → 净 −11.7ms。

> **延迟代价 100% 来自 decode 长度。** 把输出从"50 篇全排列"改成"前 10 名"，
> **333ms 全部消失，而池子仍是 50 篇** → **「池子深度 K」与「输出长度」成功解耦，
> K 从此可按召回需要自由选，不再受延迟约束。**
> 与 ②-B 否定"廉价**输入**表示"不矛盾：那里改**输入**（掉 10.6pt），这里改**输出**（涨 0.17pt，不显著）
> —— **输入与输出是两个独立的成本轴。**

⚠️ **呈现顺序的噪声地板 ≈ 1.3pt**：同一 `k50` 配置，缓存里（`llm_rerank.py`）全量 597 题
测得 R@5 = **0.7638**，本次测得 **0.7511** —— 模型/温度/候选集完全相同，**只差候选呈现的随机排列**。
→ 本实验的 `+3.50pt` **高于**该噪声地板；而 `+0.17pt` **落在**地板内（是"打平"，不是"更好"）。

**过程备注**：首次跑到题 444 时 API **余额耗尽**（`HTTP 402`），只完成 445 题；
充值后用 `--resume-from`（并入旧结果）+ `--only-q`（精确补单题）补齐到全 597。
⚠️ 踩坑：`--n > 0` 时 `qidx` 是 `rng.choice` 的**随机样本**，其下标 **≠ 题号** ——
补单题必须用 `--only-q`，不能用 `--start`。

## 阶段 ②-C：三种"改进候选池"方案的**系统性失败**（根因：pointwise 判别力天花板）

三个想法都用**免费探针**先验证（`_scratch/union_probe.py`、`onehop_probe.py`、
`ce_onehop_eval.py` 与拆分脚本），全部在花 LLM 钱之前得出结论。

### 想法① 多路召回并集（BM25@k ∪ dense@k ∪ hyb0.5@k）→ **不成立**

| 方案 | 池子大小 | 并集覆盖 | **同预算 hyb0.5** | Δ |
|---|---|---|---|---|
| bm25@30 ∪ dense@30 ∪ hyb0.5@30 | 57.1 | 0.7825 | **0.7955** | **−1.31pt** |
| bm25@50 ∪ dense@50 ∪ hyb0.5@50 | 92.2 | 0.8101 | **0.8333** | −2.32pt |
| bm25@30 ∪ dense@30 | 53.7 | 0.7724 | 0.7922 | −1.98pt |

**致命证据**：`bm25@30 ∪ dense@30 ∪ hyb0.5@30` **平均新增 0.0 篇**（在 hyb0.5 top-100 之外）
→ **完全是子集**。原因：**`hyb0.5` 本身就是 BM25 与 dense 的 RRF 融合**，
任一路排前 30 的文档在融合列表里排名必然不低 → **RRF 已把多路信息用掉**。

> 直觉"不同检索器盲区不同"没错，但这**两路的盲区相同**（都是 title+abstract 匹配）。

### 想法② one-hop 引用扩展（CE 两趟版）→ **上界 +9.2pt，实际 +0.17pt**

设计（**LLM 成本不变**，是它相对"扩 K"的最大优势）：

```
第一趟：hyb0.5 top-100 → CE → 取 CE top-20 作为 seed
扩展  ：seed ∪ (seed 的 outgoing references ∩ 语料)   ← 实测平均 132.6 篇（不是 ~40）
第二趟：CE 对新池重新打分 → 取 top-20 → 交给 LLM（仍是 20 篇）
```

**纯查表（$0）阶段**：

| seed-K | 池均值 | gold 覆盖率 | vs ce top-20 |
|---|---|---|---|
| 10 | 71.8 | 0.7768 | +3.4pt |
| **20** | **132.6** | **0.8350** | **+9.2pt** |
| 30 | 188.6 | 0.8568 | +11.4pt |
| 50 | 295.0 | 0.8832 | +14.0pt |

→ **ce top-20 + 引用邻居的覆盖率 = 0.8350 = ce top-100 的覆盖率**，
而 **LLM 成本只有 1/4.7**（4,082 vs 19,304 token）。且「gold 只在引用邻居里」有 **52 条（8.7%）**。

**免费 GPU 验证**（`ce_onehop_eval.py`，86 对/s，17 分钟）：

| 方案 | gold@1 | gold@5 | gold@10 | **gold@20** | gold@50 |
|---|---|---|---|---|---|
| ce top-20（现用） | 0.4154 | 0.6168 | 0.6735 | **0.7430** | 0.7430 |
| **one-hop（ce20 + 邻居 → CE 重排）** | 0.4154 | 0.6168 | 0.6768 | **0.7447** | 0.8219 |
| ce top-100（4.7× 成本） | 0.4154 | 0.6168 | 0.6735 | 0.7430 | 0.8132 |

**拆解**：保住 449 条 / **新捞回 3 条** / **挤掉 2 条** → 净 **+1 条**。
那 52 条"gold 只在引用邻居里"的查询，**只捞回 3 条（6%）**。

**根因**：**CE 的新旧 top-20 重合度 0.959**（中位 0.950；49.1% 的查询完全一样，93% ≥ 0.90）
→ **CE 看 20 篇和看 143 篇，选出的前 20 是同一批**。
逐点打分下，引用邻居与真金的分数落在同一区间，仍输给"字面上最像"的。

### 统一结论：四种"改候选池"的方式全部无效

| 尝试 | 上界变化 | **实际输出变化** |
|---|---|---|
| 多路并集 | −1.3pt（反降） | — |
| 扩 K（20→100） | +9.2pt | R@1 **+0.00pt** |
| 引用邻居 one-hop | +9.2pt | gold@20 **+0.17pt** |
| 廉价表示粗筛 | −10.6pt（反降） | — |

> **瓶颈不在候选池，在 pointwise 精排的判别力天花板。**
> 在「K=20 + pointwise 筛选」这个成本档位上，**我们已经到顶**。
> 唯一出路是换**排序范式**：listwise 做筛选（ce top-100 + LLM 一次排 100，覆盖率 81.3%）
> —— 但那是 5.6× 成本；或换更强的 pointwise 模型（未测）。

## 阶段 ②-D：**引用关系放进"排序"才有效**（免费 +1.37pt，CV 已验证）

上一步的结论是"四种改**候选池**的方式全部无效"。但这里有一个更细的区分：

| 引用信息怎么用 | 结果 |
|---|---|
| 放进**候选集合**（one-hop append + CE 重排） | ❌ gold@20 **+0.17pt**（CE 新旧 top-20 重合度 95.9%） |
| **放进排序**（显式算成分数并融合） | ✅ gold@20 **+1.37pt**（**CV 验证稳健**） |

**根因**：CE 是 pointwise，只看 `(query, doc)` 文本 —— **"这篇被第 1 名引用了"这个信号对它根本不存在**。
而论文用 GPT-4o listwise 且把邻居**紧跟在其引用者后面**，LLM 能从位置读出这条关系
（这解释了论文 BM25 **+4.9pt** 与我们 **+0.17pt** 的差异）。

**做法**（`_scratch/citation_signal_fuse.py`，纯计算 $0）：

```
pool        = ce top-20 ∪ (ce top-20 的 outgoing references ∩ 语料)   ← 平均 132.6 篇
cit_score(d)= Σ_{s ∈ ce20, d ∈ cites(s)} 1 / rank(s)                 ← 被排名越高的 seed 引用，分越高
fuse        = z(ce_score) + β · z(cit_score)
```

| β | gold@1 | gold@5 | gold@10 | gold@20 |
|---|---|---|---|---|
| 0.0（纯 CE） | 0.4154 | 0.6168 | 0.6768 | 0.7447 |
| 0.1 | 0.4210 | 0.6285 | 0.6819 | 0.7511 |
| **0.2** | 0.4180 | **0.6302** | 0.6877 | **0.7567** |
| 1.0 | 0.2781 | 0.5372 | 0.6427 | 0.7329 ← 权重过大崩掉 |

**5 折交叉验证**（训练折选 β、测试折评估）：

| 指标 | 固定 β=0 | **CV 选 β** | **CV 增益** | 每折选中的 β |
|---|---|---|---|---|
| gold@1 | 0.4154 | 0.4176 | +0.22pt | 波动 0.08~0.15 |
| gold@5 | 0.6168 | 0.6210 | +0.42pt | 波动 0.08~0.30 |
| gold@10 | 0.6768 | 0.6880 | +1.12pt | 波动 0.30~0.50 |
| **gold@20** | 0.7447 | **0.7567** | **+1.21pt** | **[0.2]×5 ← 完全一致** |

→ **gold@20 的增益不是过拟合**（CV 增益 = 全量最优）。
→ **该信号主要改善"筛选"（把 gold 纳入前 20），不改善"排第一"（gold@1 仅 +0.22pt）。**

**与 LLM 的分工正好互补**：
```
引用信号擅长   把 gold 捞进前 20     ← CE 做不到（重合度 95.9%）
LLM listwise 擅长  在给定 20 篇里精排  ← 捕获率 82%
```
→ LLM 成本不变（仍看 20 篇），额外只有 CE 一趟（GPU 免费）+ 融合计算（$0）。

**成本汇总**：本阶段全部为**免费计算**，未新增 LLM 费用。

## 阶段 ②-E：融合候选喂 LLM 的实测（**同成本下无可靠改善**，但机制清晰）

用「引用信号融合」后的 top-20（`build_fused_cands.py` → `fused_cands_k20.npy`）
替换默认候选，喂同一个 LLM（`llm_rerank.py --cands-file --arms C`，成本不变）。

**配对对比**（同一批 597 条、同一 LLM、同一 doc-view）：

| 指标 | 臂 B（ce top-20） | 臂 C（融合候选） | Δ | McNemar p |
|---|---|---|---|---|
| **R@1** | **0.6092** | 0.5905 | **−0.0187** | 0.104（不显著） |
| R@5 | 0.7195 | 0.7241 | +0.0045 | 0.856 |
| R@10 | 0.7271 | 0.7450 | +0.0179 | 0.087 |
| R@20 | 0.7430 | **0.7567** | **+0.0137** | （= 池子覆盖率，确定性） |
| **MRR@10** | **0.6726** | 0.6623 | −0.0103 | — |

**所有差异都不显著** → **同成本下不能可靠改善**，不应替换默认配置。

### 机制（本阶段最有价值的发现）：**LLM 的捕获率下降**

```
LLM 捕获率 = R@1 ÷ 候选集上界
  臂B：0.6092 / 0.7430 = 82.0%
  臂C：0.5905 / 0.7567 = 78.0%   ← 候选集更好，但 LLM 识别能力反而降 4pt
```

引用邻居是**语义检索漏掉的**文档 —— 其摘要与查询的语义重合度本就低（所以第一阶段找不到）。
**LLM 只看文本，面临同样的困难。**

> **两种排序器（CE pointwise 与 LLM listwise）都认不出这些文档**：
> 它们的可识别线索**不在文本里，而在图结构里** —— 而两者都读不到。

### 五种"改候选池"的方式全部无法突破 R@1

| 尝试 | 候选集上界 | **R@1** |
|---|---|---|
| 多路并集 | −0.013 | — |
| 扩 K（20→100） | +0.092 | **+0.0000** |
| one-hop append | +0.092 | （gold@20 +0.0017） |
| 廉价表示粗筛 | −0.106 | — |
| **引用信号融合** | **+0.0137** | **−0.0187（不显著）** |

> **`R@1 = 0.6092` 是硬天花板。** 候选池质量的提升全部停留在"排序器认不出"的那类文档上。

### 由此得到的新线索（下一步）

**既然引用信息能提升候选集、但排序器读不到 → 就把引用关系直接写进 prompt**：

```
1. 标题：…
2. 标题：…  ← 被第 1 篇引用          ← 显式给出结构信号
3. 标题：…
```
这正是论文的做法（其拼接顺序 `p1, p1引用的, p2, p2引用的` 让 LLM 从**位置**推断，
我们改为**显式标注**）。成本每篇多 3~5 token，几乎不涨。

## 阶段 ②-F（收尾）：引用标注喂 LLM —— **R@1 仍是天花板，但深位指标显著改善**

**思路**：前面所有尝试都在改"给排序器什么候选"，但**信息始终到不了排序器**。
这一步反过来 —— 把引用关系**显式写进 prompt**，让排序器"看得见"：

```
1. 标题：…
2. 标题：…      ← 被第 3 篇引用        ← 显式标注（论文靠相邻位置隐式表达）
3. 标题：…
```
（图例只出现在臂 D 的 user message，`_SYS` 不变 → **C 与 D 只差"标注"这一个变量**。
标注覆盖率：**99.0% 的查询至少有一条标注**，平均 6.02 篇候选被标注。）

**三臂对比**（同批 597 条、同一 LLM、同一 doc-view）：

| 指标 | **B**: ce top-20 | **C**: 融合候选 | **D**: 融合+标注 | C→D | B→D |
|---|---|---|---|---|---|
| **R@1** | **0.6092** | 0.5905 | 0.6014 | +0.0109 | **−0.0078** |
| R@5 | 0.7195 | 0.7241 | **0.7266** | +0.0025 | +0.0070 |
| **R@10** | 0.7271 | 0.7450 | **0.7475** | +0.0025 | **+0.0204** |
| **R@20** | 0.7430 | 0.7567 | **0.7567** | 0 | +0.0137 |
| MRR@10 | **0.6726** | 0.6623 | 0.6699 | +0.0076 | −0.0027 |

**LLM 捕获率**：B **82.0%** → C 78.0% → **D 79.5%**（标注让捕获率回升 1.5pt）

**显著性（McNemar 配对）**：

| 对比 | hit@1 | hit@5 | hit@10 |
|---|---|---|---|
| **C vs D**（标注的作用） | 净 +7，**p=0.119**（方向对，不显著） | 净 +2，p=0.754 | 净 +2，p=0.625 |
| **B vs D**（最终对比） | 净 −5，p=0.552（不显著） | 净 +4，p=0.572 | 净 +12，**p=0.0357 显著** |

**论文口径**：

| 系统 | Broad R@20 | Specific R@5 |
|---|---|---|
| paper: GPT-4o rerank(GritLM) | 75.3 | 79.2 |
| paper: GritLM-7B | 70.8 | 74.8 |
| **ours: D（融合+标注）** | **65.0** | 76.1 |

### 最终结论

**① `R@1 = 0.6092` 是硬天花板** —— 六种方式全部无法显著突破：
多路并集（子集，无效）／扩 K（+0.00）／one-hop append（+0.00）／廉价表示（上界 −10.6pt）／
β 分数融合（−1.87pt, n.s.）／RRF 融合（恒等或崩）／**引用标注（−0.78pt, n.s.）**。

**② 但深位指标可改善**：「引用扩展 + 显式标注」带来
**R@10 +2.04pt（p=0.036 显著）**、R@20 +1.37pt、Broad R@20 **+4.0pt**，
而成本只多 **5.6%**（4,082 → 4,311 token/查询）。

**③ 推荐配置**（两者成本几乎相同，取舍取决于产品指标）：

| 产品指标 | 配置 | 主指标 | $/千次 |
|---|---|---|---|
| **最相关那一篇**（R@1 / MRR） | **B**（ce top-20） | R@1 **0.6092**，MRR **0.6726** | $0.6 |
| **候选清单**（R@10 / R@20） | **D**（融合 + 引用标注） | R@10 **0.7475**，Broad R@20 **65.0** | $0.63 |

**④ 方法论副产品**：标注使 LLM 捕获率从 78.0% 回升到 79.5%，说明
**"把信息送到排序器面前"这个方向是对的**，只是效应量在 597 条上还不足以显著。

## 阶段 ③：扩语料（arXiv 接入）—— **跨语料 RRF 是悬崖，不可用**

LitSearch 语料有两条硬边界：**NLP 领域**（ACL 家族压倒性，CVPR/NeurIPS 基本为零）
+ **冻结在 2023 年底**（2024 仅 451 篇）。本轮把 arXiv 新语料接进来。

### 3.1 数据：arXiv OAI-PMH（官方推荐路径）

| 项 | 值 |
|---|---|
| 抓取方式 | **OAI-PMH**。arXiv 官方文档称其为"批量下载 / 保持元数据最新副本的**首选方式**"，并要求**不要**程序化抓全站 |
| 规模 | **61,426 篇**（2026-07~09 为主，含少量 2024–2025 修订稿）；`set=cs:cs`，`metadataPrefix=arXiv`（含 abstract）|
| 与旧语料重叠 | **13 篇（0.02%）** → **纯新增** |
| 成本 | 原始 XML 分片 13 块 / 40.8 MB；编码 **61 行/s ≈ 17 分钟**（比 LitSearch 慢，arXiv 摘要更长：p50 1493 vs 936 字符）|

**两个踩坑**（都会静默给 0 条）：
1. `until` 超过服务端索引日期 → `badArgument: until date too late`，**整个月 0 条**（clamp 到"今天"仍不够）→ **当月不指定 `until`**；
2. OAI 的 datestamp 是**更新日**，早期月份混着大量老论文的更新 → 必须再按 `<created>` 过滤。

### 3.2 索引：完全复用同一实现（口径保证）

`build_arxiv_index.py` **直接 import** `eval_retrieval.SparseBM25`，向量沿用 `encode_corpus.py` 口径
（bge-m3 / max_len 512 / 归一化 / 分块续跑）。融合时口径必须一致，否则融合本身就是错的。

### 3.3 ★ 负结果：跨语料 RRF 融合是一个**悬崖**

`eval_multi_corpus.py --mode rrf`，597 题（gold 全在**旧**语料 → 新语料 = 纯干扰项）：

| w（新语料权重）| R@1 | R@5 | R@100 | 新语料进top5 |
|---|---|---|---|---|
| **0（基线）** | **0.3548** | **0.5475** | **0.8350** | 0 |
| 0.35 | 0.3548 | 0.5475 | 0.8274 | 0 |
| 0.45 | 0.3548 | 0.5475 | 0.8022 | 0 |
| **0.50** | 0.1873 | 0.4680 | 0.7838 | 2.48 |
| **0.55** | **0.0000** | **0.0000** | 0.7679 | **5.0** |
| 0.65 | 0.0000 | 0.0000 | 0.6839 | 5.0 |

- `w ≤ 0.45` → 新语料**进不了 top-5**（形同不存在），而 R@100 已在掉；
- `w ≥ 0.55` → **top-5 被新语料占满**，旧语料 gold 全被挤出 → **R@5 归零**（p=5.7e-101）。

**根因**：RRF 是 **rank 计分**。两路都产出 1..1000 的名次 → **两路分数完全同尺度** →
权重稍过 0.5 就一方通吃。**"两个语料的相对可信度"不是 rank 能表达的。**

> 这是 `equal_rrf` 被证否的**同一家族错误**（用等权 rank 融合表达一个**非对称**的信任关系），
> 但更极端：不是"收益变小"，而是**直接归零**。
> 顺带否定 `quota_union` 用于此处：它**结构上保证不退化**，但也**保证新语料永远进不了头部**
> → 对"交付 top-5"等于没接（`--mode quota`）。

### 3.4 正解方向：score-based 候选合并 + CE 精排

`--mode ce`：合并两路**候选集合**（旧 top-K₁ + 新 top-K₂），交给 `bge-reranker-v2-m3` 用
**分数**定序 —— 绕开 rank 归一化。用 `--ce-pool 100,0` 作对照以隔离"CE 重排"与"新增候选"两变量。
产物：`LITSEARCH_CE100-*_MULTI_CORPUS.md`。
