# C3 验证器标定：NLI 能否替代 / 分担 LLM 判官？（2026-09-30）

`_r2_nli_calib.py`（1555s 推理 + 26s 汇总）｜ 修订统计 `_r2_nli_sep.py`
｜ 产物 `results/R2_NLI_CALIB_{DOC,CHUNK,T1,T1_FIXED,T2,T3}.csv` + `results/nli_cache/*.npz`

**做法（零新标注）**：拿已有的 **1,400 对 (facet, 篇) LLM 判官真值**（`gold_final3.csv`，
覆盖每 facet 全部 50 篇），对**同一批对子**算 4 个候选验证器的分，看谁能复现 LLM gold。

| 验证器 | 假设 | 成本 | 说明 |
|---|---|---|---|
| `regex` | — | **¥0** | `_m.judge()` 词面锚点（判据正则） |
| `rerank` | 题面+子查询 | ¥0（本地） | `bge-reranker-v2-m3` —— **相关性**，非蕴含 |
| `nli_xnli` | **中文论断** | ¥0（本地） | `mDeBERTa-v3-base-mnli-xnli`（多语，跨语言） |
| `nli_fever` | **英文 `para`** | ¥0（本地） | `DeBERTa-v3-base-mnli-fever-anli`（FEVER 调过） |

⚠️ **偏置声明**：LLM gold 是**带判据**做的。`regex` 的判据正则与 LLM 所见的判据**同源**
→ 它的分数**部分是"同源优势"**，不是独立证据。**不能据此说"regex 能替代 LLM"。**

## 表① ★ 判别力（篇级，1,400 对，随机 AUC = 0.5）

| 验证器 | **AUC** | 逐 facet Cohen's d | d 中位 | 负 d 的 facet | d>0.5 占比 | best-F1 |
|---|---|---|---|---|---|---|
| **`regex`** | **0.737** | **+1.487** | 1.124 | **0/28** | **78.6%** | **0.583** |
| `rerank` | 0.623 | +0.469 | 0.399 | 5/28 | 42.9% | 0.498 |
| `nli_fever` | 0.605 | +0.381 | 0.515 | 6/28 | 53.6% | 0.483 |
| **`nli_xnli`** | **0.532** | **+0.118** | 0.108 | 9/28 | 17.9% | 0.449 |

> ⚠️ **统计口径已修正**：初版"分离度"用**跨 facet 混池**的 `(gold均 − 干扰均)/全体std`，
> 被各 facet 的分数尺度差异污染（一度显示 rerank 为**负**）。改为**逐 facet 标准化**后，
> 四者**全部为正** → **rerank 不是系统性反向**，只是"比随机好一点"。**别混为一谈。**

### ★ 结论 1：**多语 NLI（中文论断）在我们任务上基本无效**（AUC 0.532 ≈ 随机）
- 跨语言（中文论断 vs 英文块）+ **通用 entailment 定义** ≠ 我们的**具体证据判据**
- 换成**英文假设**（`nli_fever`）好一些（0.605），但仍**远低于 `regex` 0.737**
- 原因：ALCE 的 NLI 用法是**句级**（短 premise）；本轮是**块级**（2,001 字符）→ **这是 NLI 的下界，不是上限**

### ★ 结论 2：`regex`（零成本）判别力最强，**0/28 个 facet 为负**
→ 说明**我们的 facet 判据大部分是"词面可查"的**。
⚠️ 但含**同源成分**（见上），**不可**推断"可省掉 LLM 判官"。

### 结论 3：`rerank` 判别力中等（0.623 / setF1 0.343）
→ 与上一轮"**重排显著负收益**（ΔsetF1 −0.099, p=1.000）"一致：
**它的绝对判别力低于多列表融合共识的水平**，所以"用重排替换融合分"会掉。

## 表③ ★★ 级联可行性（**本轮最有价值的一张表**）

按 τ 逐块过滤后：**块保留比** vs **gold 篇留存率**（= gold 篇中"至少有一个块存活"的比例）

| 验证器 | τ | 块保留比 | **gold 篇留存** |
|---|---|---|---|
| `nli_xnli` | 0.05 | 52.0% | **99.8%** |
| `nli_xnli` | **0.10** | **38.1%** | **99.1%** |
| `nli_xnli` | 0.20 | 25.9% | 90.8% |
| `nli_fever` | 0.05 | 40.7% | **98.9%** |
| `nli_fever` | **0.10** | **30.2%** | **97.6%** |
| `nli_fever` | 0.20 | 19.6% | 93.7% |
| `regex` | 任意 | **9.1%** | **79.8%** |

### ★★★ 结论 4（反直觉，也是答案）：**NLI 判别力差，但作为"粗筛"极有用**

- `nli_xnli` τ=0.10：**筛掉 61.9% 的块**，而 **gold 篇只漏 0.9%**
- `nli_fever` τ=0.05：筛掉 59.3% 的块，gold 篇漏 1.1%
- 对比 `regex`：虽 AUC 最高，但是**硬阈值** → 筛掉 90.9% 的块时 **gold 篇漏掉 20.2%**

→ **两者角色互补、不可互相替代**：
| 角色 | 该用谁 | 理由 |
|---|---|---|
| **精判（判别力）** | **`regex`**（AUC 0.737） | 判据正则最贴近操作性判据 |
| **粗筛（高召回）** | **NLI**（τ 低） | 弱排序 + 连续分数 → 能"宽进"地砍掉 6 成块而不丢 gold 篇 |
| **最终 verify** | **仍然是 LLM** | 判据是 prompt 给的，regex/NLI 都无法完全复现 |

## 回答你的问题：**要不要用 NLI 模型？**

| 问法 | 答 |
|---|---|
| **用 NLI 替代 LLM 判官？** | ❌ **不要** —— 判别力不够（最好 `nli_fever` AUC 0.605，差的 0.532≈随机；`regex` 0.737），且**无法读我们的判据** |
| **用 NLI 做级联粗筛？** | ✅ **要** —— τ≈0.05~0.10 → **块减 60%、gold 篇留存 >99%** → **LLM 调用省 ~60%**，几乎不漏 |
| **成本还贵吗？** | 实验规模本来就不贵（28 题 ≈ ¥10）。**级联把生产规模的 LLM 账单再砍 60%**，且 NLI 本地零边际成本 |
| **ALCE 怎么说？** | ALCE 的 φ 判定器**本来就是 NLI**（TRUE），我们 `judge()` 的注释早预留了这个插槽 → 用 NLI **不是降级**，但**ALCE 是句级**，本轮块级是下界 |

### 推荐架构（级联，非二选一）
```
map（独立召回，高召回优先）
   NLI τ≈0.05~0.10 粗筛  →  块 -60%，gold 篇留存 >99%
        →  幸存块
verify（逐条验证，高精度优先）
   ① regex 命中 → 直接判正（零成本，判别力最强）
   ② 未命中 → LLM 精判（只判幸存者，调用量 -60%）
```

## 边界（必须写清）
1. **`regex` 的高分含"同源"成分**（判据正则 ↔ LLM 判据同源）→ **不可**推断能省掉 LLM。
2. **NLI 是块级（2,001 字符、截断 512 token）**，而非 ALCE 的**句级** → 这是 NLI 的**下界**；
   句级 + 更强模型（TRUE / MiniCheck / HHEM）**未测**。
3. **"gold 篇留存"是篇级口径**（≥1 块存活）；**块级**留存低得多（`nli_xnli` τ=0.1 仅 41.2%）
   → 若 C3 要定位**具体证据句**，60% 的削减会伤到"句级证据完整率"，需另测。
4. 假设只用**中文论断**（`nli_xnli`）与**英文 `para`**（`nli_fever`）；`anchor`/子查询作假设**未测**。
5. 单次运行、28 facet；未做配对自举（本表是描述性对照）。
6. τ 是在**本语料**上选的 → 换语料需重标定（但曲线可复用）。

## 工程教训（已固化进脚本）
1. **`huggingface.co` 被墙、`hf-mirror.com` 小文件通但 ~1GB 大文件 TLS 卡死**
   → `curl -L --retry` 下到本地目录（`_nli_curl.py`），`from_pretrained(本地目录)`。
2. **6GB 卡上模型不能共驻**（第 2 次踩到）：显存耗尽时 Windows 驱动**换页**→ GPU 100% 但零进展。
3. **DeBERTa-v3 的解耦注意力很吃显存**：reranker 能 batch 64，DeBERTa **batch 16 才安全**。
4. **按块长排序再批**（`padding=True` 补到批内最长）→ 实测 **3.8× 加速**；**bf16** 再加 ~2×。
5. **逐臂逐簇落盘缓存**（`npz`）：第一版 rerank 跑 9 分钟后在 NLI 阶段被杀，**全丢重跑**。
