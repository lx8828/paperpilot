→ **下游是「独立召回 + 逐条验证」（高召回优先）→ 用 +0.004 的 setF1 换 +14pt 覆盖率，明确划算。**

**`rerank` 在 8 个 k 上全部更差，`setF1` 与 `α-nDCG` 双双显著为负。**

**机制（与我们 9 月的既有发现完全一致）**：
- RRF 融合的块分是 **7 路投票的共识** → 天然抗噪、抗"语义相似陷阱"；
- `bge-reranker` 是 **pointwise cross-encoder**：只看 `(query, 块)` 对的语义相关性 →
  **系统性地把"语义最像的"排前面，从而丢覆盖度**；
- `R2_PRIOR_ART_20260928.md` 已记录过同一现象：*"CE（pointwise，永远把语义最像的排前面）在**覆盖率**上
  反而比融合差（交付 20 篇：21% vs 27%）"*，且 **CoverageBench** 的结论正是
  *"为相关性优化 → 系统性丢覆盖度"*。
- → **本次是在 50 篇口径上的独立复现，且首次给出显著性检验。**

**根因**：我们的任务是**多篇覆盖**（一个 facet 常对应十几篇 gold），**不是单篇排序** →
pointwise rerank 的优化目标与任务目标**错配**。

> ⚠️ 边界：只测了 pointwise CE（`bge-reranker-v2-m3`，`query = 题面 + 子查询拼接`）。
> **listwise / setwise rerank、或"只在池内重排但保覆盖"的做法未测**，不能一概而论。

## ★ 关于「独立召回 + 逐条验证」加在哪（你的问题）

**它不在排序链里，是"交付 top-k 篇"之后的下游阶段** —— 字典依据：`R2_CHUNK_SWITCH_TODO_20260929.md` 的 **C3**：

> **C3 独立召回 + 逐条验证**（answer recaller 逐段落独立预测，优先高召回 → 逐候选独立验证）；
> QAMPARI 线做过（`passage_union` / `passage_verified`）；**R2 线完全没做**。这是 **ALCE 的 map-reduce + verify**。

```
中文题面 ─1路 dense─┐
英文子查询×3 ─dense─┼─每路截 top-d─→ RRF 融合(ρ=1:4)─→ 候选池 C（≈247 块）
英文子查询×3 ─BM25──┘                                        │
                                    （重排 ❌ 本次证明为负收益，不加）
                                                             ↓
                                              段级聚合（篇内 max）→ 截断 top-k 篇
                                                             ↓
                                                        【交付】
                                                             ↓
        ┌───────────────── C3（不在本流水线内）─────────────────┐
        │  map（独立召回）：对每个交付篇的**每个段落**独立问     │
        │      "这段支持该 facet 吗？" —— **不做段落间比较**   │
        │  verify（逐条验证）：对 map 出的证据逐条独立复核      │
        └──────────────────────────────────────────────────────┘
```

### 为什么"独立"是刻意的（与我们的实验直接呼应）
排序是**比较性**的（块之间比大小），C3 是**非比较性**的（逐段独立判定）→
**不继承排序偏差**。这也解释了 `R2_SCORE_VS_RANK_20260930.md` 里那条"与下游协同"的论点：
*"下游是独立召回 + 逐条 LLM 验证 → 排序只需把候选排进前 k，不需要精确相对分数"* ——
**本次的负收益重排实验正好证明了这一点：精修相对分数（CE）不但没用于下游，反而损害了候选的覆盖。**

### ★ 它反过来决定 k 的判据（→ 这就是你问的"13 要重测"的答案）
因为 C3 是**高召回优先**：
1. **k 不该由 `setP ≥ 0.40` 这类精确率约束来定** → 改为看 `StRecall@k`（覆盖率）；
2. 本次据此把 **k=13 → k=20**（setF1 持平，覆盖率 +14pt）；
3. k 的**上界**应由"验证阶段能吞多少候选"（LLM 成本）决定 —— 那是个成本问题，不是排序问题。
