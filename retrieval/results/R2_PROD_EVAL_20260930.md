### ★ 性能修复（本轮顺手挖出的生产 bug）

**症状**：整簇 1,079 块编码把显存打满 **5,634 / 6,144 MiB**（剩 287）→ Windows 驱动换页 →
**>1,000s 且不收敛**。根因：`_get_model()` 加载 bge-m3 **无半精度**（fp32），且
`padding=True` 补到批内最长 → 真正驱动激活量的指标是 **`batch_size × 批内最长 token`**。

用真 tokenizer 在**本语料 3,284 块**上实测（`_verify_padding_peak.py`）：

| 分批策略 | 总 token | **单批 token 峰值** |
|---|---|---|
| 乱序（原行为） | 3,838,068 | **60,864** ← 打满 6 GB |
| 仅按长度排序 | 2,587,840 | **30,432** ← 仍偏高 |
| **排序 + 每批 token 预算 8,192（现）** | 2,485,939 | **8,925** ← **降 6.8×** |

**实测验证**（`_verify_encode_sort.py`）：

| | 峰值显存 | 整簇耗时 |
|---|---|---|
| 改动前 | **5,634 MiB** | **>1,000s 不收敛** |
| **改动后** | **2,539 MiB** | **94.3s** |

**无回归**：64 块打乱子集上 `max |Δ| = 0.000e+00`、逐条最小余弦 0.99999994；
**三条查询的 RRF top-10 逐位相同** ✅；不引入 fp16 ⇒ 已有 `.cvec.npy` 缓存继续有效。
（⚠️ 该子集只用短块，长块未覆盖；但批组成变化只引入 fp32 舍入级差异，与当年 `32→8` 同级）

**⚠️ 教训练**：别用"批内最长 token"当显存指标 —— 两种排序下它都是 7,608（最长的块总在某个批里）。

## 三、★ 与 dev 定稿的差距：**F1 0.619 vs 0.886（−0.267）**，首要嫌疑已定位

| | dev 定稿（`_r2_c3_window.py`） | 生产链路（本次） |
|---|---|---|
| **窗口构造** | 去重(**facet 正则命中块[:4]** ∪ 语义 top-3)[:4] | **只有语义选块**（无判据锚点支） |
| 子查询 | `subqueries_v2.json`（离线固化） | `decompose()` 动态生成 |
| 检索 | 同（7 路 RRF） | 同（`search_multiroute`） |
| 判官 | A/B + 第三轮 | 同（已接入） |
| 交付 k | top-30 | **全部 50 篇**（生产候选） |
| **P / R / F1** | **0.971 / 0.829 / 0.886** | **0.694 / 0.606 / 0.619** |

**首要嫌疑：生产窗口缺"判据锚点"这一支。**
dev 窗口有一支是 **facet 判据正则命中的块**（优先给它），生产**没有 facet 正则**（论断是用户自由文本）→ 窗口只剩"语义 top-3"。

**这个嫌疑有直接佐证**：W1 实验（`R2_C3_W1_V2_20260930.md`）已测出
**"把判据词从检索查询里去掉 → 判官在 4/4 受影响 facet 上全面变差、5/5 个 k 全更低"**。
生产窗口**整条链都缺判据词**（既不在查询、也不在锚点支）→ 与 W1 的负向机制一致。

**可测的修法**：从论断里**抽出"判定标准词/短语"**（LLM 抽或直接用论断中的英文示例词），
作为窗口的第 2 支（锚点支）—— 即把 dev 的窗口构造完整搬到生产。

## 四、边界
1. **接地判官是单判官 + 看同一批证据** → 0.772 偏乐观；要严格需**独立证据/独立协议**。
2. 生产候选 = **全部 50 篇**（非 top-k）→ 与 dev 的 top-30 口径不同；**未做 k 对齐对照**。
3. 只有一次运行；未做配对自举（P/R/F1 的 −0.267 差距**未做显著性**，但幅度远超 σ≈0.01）。
4. `2efficiency`（gold 2）、`2error_analysis`（gold 3）等**极小样本**对均值有拉扯。
5. 生产检索的 `_select`（节级配额）与 dev 的纯 RRF 序**不完全一致**，未归因。
6. `decompose()` 每次调用生成子查询（**无缓存**）→ 同题重跑会有波动。
