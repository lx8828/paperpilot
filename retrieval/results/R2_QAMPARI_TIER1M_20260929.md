# 1M 档评测：检索到底值不值（判决实验）

日期：2026-09-29 ｜ 基准：LoFT RAG / QAMPARI / `1m` 档（**5,878 段 / 3,395,572 字符 ≈ 849k token**，100 题）
目的：`128k` 档语料（105k token）能整档塞进上下文 → 实测**直读与检索打平**（subspan_em 都 0.700），
**无法判断检索的价值**。`1m` 档装不进上下文 → **判决场**。

---

## 0. 结论

1. **1m 档下检索是必需的，且我们的检索"召回还在"**：gold 段落的 **95.4%** 仍被捞进 top-40。
2. **掉分的主因不是检索召回**，而是 **① 排序变差（top-5 精度崩）② reader 在长上下文下退化**。
3. **单题铁证**：检索用 **0.7% 的上下文**拿到 **5/5**；直读用 **24% 的上下文**只拿 **3/5** 且开始编造。
4. **下一步靶心变了**：不是"更强召回"，而是 **重排（top-5 精度）+ reader 抗噪**——与论文语料线"判定是难点"同一方向。
5. **诚实定位**：我们的检索器（bge-m3+BM25 RRF，无重排）在 `MRecall@5` 上 **0.470 < 论文 Gecko 的 0.57**（同为 128k 档）。

## 2. 检索诊断（零 LLM，分离"检索掉"与"reader 掉"）

| 档位 | 语料段数 | R@5 | R@10 | R@20 | **R@40** | R@100 | **MRecall@5** |
|---|---|---|---|---|---|---|---|
| `128k` | 755 | 0.822 | 0.922 | 0.958 | **0.990** | 0.996 | **0.470** |
| `1m` | 5,878 | **0.514** | 0.780 | 0.890 | **0.954** | 0.980 | **0.110** |

**读数**：
- **R@40 几乎不掉（0.990 → 0.954）** → 我们喂给 reader 的上下文里**仍然有 95% 的 gold 段落**
  → **`subspan_em` 掉 0.32 不能归因于"检索没召回"**
- **R@5 掉很多（0.822 → 0.514）**，**MRecall@5 崩（0.470 → 0.110）** → **排序质量退化**（前 5 名堆更多噪声）

**与论文对齐（Text Retrieval / QAMPARI / `MRecall@5`，128k 档）**：

| 系统 | MRecall@5 |
|---|---|
| Gemini 1.5 Pro | 0.61 |
| **Specialized（Gecko，top-40 + Gemini 读）** | **0.57** |
| **我们（bge-m3 + BM25 → RRF，无重排）** | **0.470** |
| Claude 3 Opus | 0.20 |
| GPT-4o | 0.18 |

→ **我们高于两个通用长上下文模型，但低于专门训练的 Gecko**。这是可对外讲的诚实定位。

## 3. ★ 单题铁证：长上下文 ≠ 检索的替代品

`qid=1314`，gold **5** 个答案。同一道题，只改"给模型多少上下文"：

| 方式 | 上下文占语料 | 命中 gold | 备注 |
|---|---|---|---|
| **检索 top-40** | **0.7%**（25,350 字符） | **5 / 5** | ✅ 全中 |
| 直读前 100k 字符 | 2.7% | 1 / 5 | |
| 直读前 200k 字符 | 5.4% | 1 / 5 | |
| 直读前 400k 字符 | 10.7% | 2 / 5 | |
| 直读前 900k 字符 | **24.1%** | **3 / 5** | ⚠️ **开始编造**（`2016 Charlottesville…`、`2018 BNP Paribas…` 不在 gold） |

→ **上下文从 0.7% 涨到 24%（34 倍），命中反而从 5/5 掉到 3/5 且出现幻觉。**
→ 说明模型在长上下文里**"找不到针"**（注意力稀释），**"多给"不能替代"检索"**。

（模型在 ≤225k token 时仍能返回输出 —— 上限未探到；但**答案召回随上下文增长极慢**，这才是关键。）

## 4. 因此修正的两条结论

| 旧结论（只看 128k 档） | **1m 档修正后** |
|---|---|
| 「128k 档直读与检索打平 → **检索没证明价值**」 | **仅在 128k 档成立**；1m 档下**检索是决定性的**（0.7% vs 24% 上下文：5/5 vs 3/5） |
| 「0.700 主要来自 reader + 提示，不能归功检索」 | 128k 档成立；**1m 档下这是错的**——同样的 reader/提示，只换成整档直读就崩 |
| — | **新增**：1m 档掉分主因是 **排序（R@5 0.822→0.514）+ reader 长上下文退化**，不是召回 |

## 5. 下一步（靶心已明确）

| 优先 | 做什么 | 依据 |
|---|---|---|
| **1** | **加重排**（cross-encoder / bge-reranker-v2-m3 对 top-40 重排到 top-5~10） | R@40 0.954 但 R@5 0.514 → **池子里有，排不上来**，重排是直接解 |
| **2** | **reader 抗噪**（减少上下文噪声 / 分块多次调用 / 逐段摘要） | 单题实证：上下文越长命中越少且开始编造 |
| 3 | 用 **1m 档做常态评测**（而非 128k） | 128k 档分不出方法差异（直读=检索） |
| 4 | 对照实验：把我们的 top-40 换成 Gecko 或加上重排，对齐 `MRecall@5` 0.57 | 我们的检索器仍低于 Gecko |

## 6. 边界

1. 1m 档**只测了 dense+BM25 的 RRF 一路**，未测重排/融合变体。
2. 上下文上限**未探到**（≤225k token 均正常返回），故"整档直读"的**绝对**不可行性未证实；
   但**质量不可行性已证**（24% 上下文只拿 3/5）。
3. 单题铁证是 **1 题**，代表性强但**样本量 1**；`MRecall@5` 的 0.110 是全 100 题的均值，可作补充。
4. `MRecall@5` 与论文对齐的是 **Text Retrieval 行**（找段落/文档），
   而我们的 1m 主指标 `subspan_em` 对齐的是 **RAG 行**——**两行不可混**。
5. 论文 **1M 档没有 QAMPARI 逐数据集数值**（只有按任务平均的 Figure 5），
   故 1m 档**没有逐数据集外部参照线**。
