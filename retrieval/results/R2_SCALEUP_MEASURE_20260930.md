# 「要加大到多少篇才需要检索」—— 怎么测（2026-09-30）

决策：**真值用 `deepseek-chat` 单判官**（已实测 **FN = 0.00%**、F1 0.977 vs 多数票，见
`_single_vs_vote.py`）→ 1 次调用/对，便宜。

---

## 1. 好消息：方法**完全已有**，不是从零开始

| 臂 | 已有脚本 | 已有的 N=20 结果 |
|---|---|---|
| **A 整档直读**（把 N 篇全文一次塞进去，问「哪些篇做了 X」） | **`_r2_fullread.py`**（完整实现：`【Pn】` 标记、`结论篇：P3,P7` 解析、`n_touched` 注意力代理、缓存计量） | F1 **0.773** |
| **B 检索 + 逐篇判定** | **`_r2_reader.py`** | F1 **0.817**（旧口径） |
| C 检索 top-10（无判定） | 同上 `ret_F1` | 0.539 |

**要做的只是"把 N 参数化"** ✓

---

## 2. ★ 先算物理边界：A 臂最多能读 **~117 篇**

| 量 | 值 | 来源 |
|---|---|---|
| 每篇 token（生产切块口径实测） | **6,855**（33,865 字符 ÷ 4.94） | `_r2_volume.py` |
| deepseek-chat 实测可接受上下文 | **≥810k token** | `_ctx_limit.py` |
| **→ A 臂的篇数上限** | **810k ÷ 6.9k ≈ 117 篇** | 算术 |

**这条界线有两种性质，要分清**：

| 区间 | 含义 |
|---|---|
| **N > 117** | **检索不是"更好"，是"唯一可行"**（A 臂塞不进去）→ 物理必需 |
| **N ≤ 117** | 才是**质量对比**的战场：直读何时开始"读不过来" → **N\* 在这里** |

→ **所以扫描范围自然是**：

| 档 | N | S/C（vs 128k / vs 810k） | 谁在测 |
|---|---|---|---|
| 现状 | 13~18 | 0.74~0.93 / 0.12~0.15 | 已知：检索无意义 |
| 1 | **20** | 1.07 / 0.17 | **已测过**（A 0.773 vs B 0.817） |
| 2 | **40** | 2.14 / 0.34 | ← 待测 |
| 3 | **80** | 4.28 / 0.68 | ← 待测 |
| 4 | **117** | **6.26 / 1.00** | ← 待测（A 臂物理满仓） |

**N\* = 直读质量相对检索开始显著下降的最小 N**（也就是你要的那个数字）。

---

## 3. ★ 关键澄清：测这个数字**不需要先决定 MinerU**

因为两条臂要的东西不一样：

| 臂 | 需要什么 | 与 MinerU 的关系 |
|---|---|---|
| **A 整档直读** | **全文**（不切块！） | ❌ **完全无关** —— 直读要的就是整篇原文 |
| **B 检索判定** | **切块** | ⚠️ 有关，但**不是必须** —— S2ORC 文本 + 现有切块逻辑也能跑 |

→ **所以"要不要全部 MinerU"这个决定，可以放在测出 N\* 之后**。逻辑是：

```
1. 先测 N*（两臂都用现有口径，B 臂可以先用 S2ORC + 现有切块）
2. 拿到 N* 后：
     若 N* ≈ 40~117 篇  → 全 MinerU 的解析量可接受 → 值得投
     若 N* ≥ 600 篇     → 解析成本要重新算 → 可能不值得、或改用 S2ORC
```

## 4. 怎么测（5 步，都不难）

| 步 | 做什么 | 说明 |
|---|---|---|
| **M-1** | **建扩库骨架**：`corpus_clean`(64,183 篇 S2ORC 全文) 按 `corpusid` 接入；**我们的 60 篇用 corpusid 精确对齐**（已验证交集 **60/60**） | 零 LLM |
| **M-2** | **同一大库、多档模拟**：建一个 **117 篇的库**（含全部 gold + 干扰项），A/B 两臂都只取"前 N 篇"参与 → **一次建库、四档复用** | 避免重复建库 |
| **M-3** | **A 臂**：`_r2_fullread.py` 参数化 `--n-papers`；**必须让 gold 篇均匀落在前 N 篇内**（否则档位不可比） | 复用现有脚本 |
| **M-4** | **B 臂**：`_r2_reader.py` 在"前 N 篇"上检索（k 按 `k/gold` 固定，避免 k 与库一起涨） | 复用现有脚本 |
| **M-5** | **评分**：`setpf` + 同一真值；另报 `n_touched`（注意力代理）与 token 用量 | 复用现有指标 |

**新增的工作量**：M-1 的接库 + M-2 的抽样 + 一个"多档扫描驱动脚本" → **约 1~2 小时**。

## 5. ★ 真值：N ≤ 117 时**可以直接补齐**，不必妥协

上一轮我建议"零标注只报召回"，但**算了一下成本后可以撤回**：

| 档 | 新增篇 × 14 facet | 单判官调用 | 耗时（8 并发） |
|---|---|---|---|
| 40 | 40 × 14 = 560 | 560 | ~5 分钟 |
| 80 | 1,120 | 1,120 | ~10 分钟 |
| **117** | **1,638** | **1,638** | **~15 分钟** |

→ **N 的上限只有 117 篇 → 真值补齐只要 ~15 分钟** → **完全值得**。
→ 好处：**A/B 两臂在同一份完整真值上比**（避免"库里有未标注真阳性"把两臂的 P/F1 都污染）。
→ 仅这一步的 LLM 成本：**~¥几块**。

**（这也是"N ≤ 117"这个上限带来的红利：如果目标是 600 篇，真值成本就要 ×5。）**

## 7. 风险 / 需要留意的点

1. **A 臂"塞得下"≠"读得好"** → 必须看 `n_touched`（答案里显式提到 `【Pn】` 的篇数）：
   若 `n_touched` 停在前几篇而 F1 也崩 → **注意力衰退**（而非任务不可解）—— 这本身就是重要结论。
2. **B 臂的 k 必须按 `k/gold` 固定**，否则"库变大 → 随机基线下降"会被 k 一起涨抵消掉。
3. **干扰项的选择会影响难度**：
   - **同领域随机** → 测出的是"规模压力"（随机基线下降）
   - **同领域 + 单判官筛出的"疑似正例"** → 测出的是"检索增益"（更难）
   - **建议**：两臂都用**同领域随机**起步（先拿到 N\* 的量级）；若曲线平，再换难干扰项。
4. **文本口径**：全切 S2ORC 会丢掉 MinerU 的解析改进 →
   本次结论只能**迁移"S/C → 何时需要检索"的规律**，不能迁移绝对指标。
5. `corpus_clean` 的 `full_paper` 需**抽检几篇**确认不是空的/截断的（我们 60 篇的 corpusid 都在，但要确认 `full_paper` 非空）。
